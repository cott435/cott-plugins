# 01 — run-evals

Phase 1. Adds `run-evals`, the automatic skill that owns plugin-dev's eval loop: mechanical
checks, a load check, and behavioral runs of a target against a baseline, graded assertion
by assertion with skill-creator's grader, aggregated with its benchmark script and shown in
its viewer, then recorded with `log-eval`. Also the workspace layout skill-creator's scripts
expect (in a gitignored `evals/workspace/`, never under `skills/`), the committed eval-set
schema, and the helper script that builds both. The trigger kind is stubbed as "phase 2" in
eval-kinds.md; nothing else refers to it yet. The gap it closes: every phase says "run its
evals" and none says how.

Before any edit, run the phase-0 platform-fact evals E0.1–E0.5 (below) — their answers
decide details of `references/skill-creator.md` and `eval_workspace.py locate-skill-creator`.

## Decisions

- **Config directory names** follow skill-creator: `with_skill` for the target, and for the
  baseline `without_skill` (a new target, no prior version) or `old_skill` (a changed target,
  the snapshot at a git ref). Its `aggregate_benchmark.py` labels configurations from these
  names. Used for agents too, for the same reason.
- **Expectations, not assertions,** is the field name in sets, matching skill-creator's
  `references/schemas.md` and its grader's input. Prose may say "assertion".
- **Executors write their own `transcript.md`** — a subagent cannot export its transcript,
  and skill-creator's grader requires a `transcript_path`. E0.3 checks the grader accepts it.
- **The baseline snapshot is a whole directory** (`git archive <ref> <target dir>`), so a
  skill's `references/` and `scripts/` come with it.
- **One run per configuration** by default; a set eval may carry `"runs": N`.

## Specification

### `skills/run-evals/SKILL.md`

Frontmatter, verbatim (automatic — no `disable-model-invocation`; the scoping clause is
required by this plugin's `CLAUDE.md`):

```yaml
---
name: run-evals
description: Run the evals for one skill or agent of a Claude Code plugin - mechanical checks, a load check, behavioral runs against a baseline graded assertion by assertion with skill-creator's grader, benchmark and viewer, and trigger tests for skills the model invokes - then record the result with log-eval. Use only inside a plugin's own subdirectory (one containing .claude-plugin/plugin.json), whenever a phase note or a change calls for evals, or before claiming that a skill or agent behaves a certain way.
---
```

Headings, in order: `# Running a target's evals`, `## What a run is`, `## The kinds`,
`## The set`, `## The workspace`, `## The behavioral loop`, `## Review`,
`## When skill-creator is missing`, `## Record`.

Rules each section must state (wording may differ; the substance may not):

- **What a run is** — one target (a skill or an agent), one set file, one iteration. A run
  starts from `evals/sets/<target>.json`; a test that is not in a set is added to it first,
  so the next change can rerun it.
- **The kinds** — names all five kinds as backticked words — `mechanical`, `load`,
  `behavioral`, `trigger`, `platform-fact` — and points to `references/eval-kinds.md` for
  each one's method. Order within a run: mechanical, then load, then behavioral, then
  trigger; a failing mechanical check stops the run (a broken bundle makes behavioral runs
  meaningless).
- **The set** — the schema, as a fenced JSON block:

  ```json
  {
    "target": "plan-phases",
    "target_path": "skills/plan-phases/SKILL.md",
    "evals": [
      {
        "id": 1,
        "name": "trading-research-three-jobs",
        "kind": "behavioral",
        "baseline": "previous",
        "harness": "evals/sets/files/plan-phases/trading.md",
        "prompt": "/plugin-dev:plan-phases --new trading-agents a plugin for stock research agents",
        "expected_output": "one sentence a reviewer can hold the output against",
        "files": [],
        "expectations": ["an observable statement about outputs/ or transcript.md"],
        "added_in": "0.9-evals phase 0"
      }
    ]
  }
  ```

  `baseline` is `none` (new target), `previous` (the target as of the commit the current
  phase started from — `git merge-base HEAD <default branch>` for a change, the phase's
  parent commit otherwise), or an explicit git ref. `harness` is optional and required for a
  target that asks the user anything. Every expectation is observable in `outputs/` or
  `transcript.md`; "is good quality" is not an expectation. `eval_workspace.py validate`
  enforces the shape.
- **The workspace** — `evals/workspace/<target>/iteration-N/`, gitignored, never under
  `skills/` (skill-creator's default `<skill>-workspace/` sibling would be picked up by
  `check-contracts`' `skills/*` globs and by `build-site`). The layout, verbatim:

  ```
  evals/workspace/<target>/iteration-N/
  ├── baseline-snapshot/                   git archive of the target's directory at the baseline ref
  ├── eval-<id>-<name>/
  │   ├── eval_metadata.json               {eval_id, eval_name, prompt, assertions}
  │   ├── with_skill/
  │   │   ├── eval_metadata.json           same file again — the viewer reads it here
  │   │   └── run-1/{outputs/, transcript.md, grading.json, timing.json}
  │   └── old_skill/ | without_skill/      same shape
  ├── benchmark.json, benchmark.md         aggregate_benchmark.py
  └── feedback.json                        the viewer, after review
  ```

- **The behavioral loop** — the steps, numbered:
  1. `python3 ${CLAUDE_SKILL_DIR}/scripts/eval_workspace.py validate evals/sets/<target>.json`
  2. `… init . <target> [--evals 1,2,3]` — prints a JSON manifest of runs.
  3. Spawn every run in the manifest **in one message**, with-target and baseline together,
     using the executor prompt below. As each finishes, `… timing <run_dir> --tokens N
     --duration-ms N` from its completion notice — the only place those numbers exist.
  4. One grader per run, prompt below.
  5. From the skill-creator directory: `python3 -m scripts.aggregate_benchmark
     <iteration-dir> --skill-name <target>`.
  6. The viewer (see **Review**).
  7. Read the grader's critique of the expectations themselves: an expectation it calls
     trivially satisfied is rewritten in the set, in this change.

  The executor prompt, verbatim with `<…>` filled:

  > You are testing `<target>` by executing it. Read `<target file, or the snapshot's copy
  > for the baseline>` and follow it as if the user had typed: `<prompt>`. The repo is
  > `<repo root>`.
  > Harness rules — these override the target where they conflict:
  > - There is no live user. Wherever the target would ask, write the question and its
  >   options to `outputs/interview.md`, then answer from `<harness>` (or the option marked
  >   Recommended when it does not cover the question) and continue.
  > - Do not publish, commit, push, create branches, or write anywhere in the repo. Write
  >   whatever you would publish or write into `<outputs_dir>` instead.
  > - Keep `<run_dir>/transcript.md`: each step, what you read, what you decided, and your
  >   final message to the user.
  > - Stop at the target's first approval point, or when the task is done.
  > Reply with a two-line summary.

  For a `without_skill` baseline the first sentence becomes "Do the following task as you
  would without any special instructions:" and no target file is named.

  The grader prompt, verbatim with `<…>` filled:

  > Read `<skill-creator>/agents/grader.md` and follow it. expectations: `<the eval's
  > expectations as a JSON list>`. transcript_path: `<run_dir>/transcript.md`. outputs_dir:
  > `<run_dir>/outputs`. Write `<run_dir>/grading.json` with an `expectations` array whose
  > items have exactly the fields `text`, `passed`, `evidence`, and a `summary` with
  > `passed`, `failed`, `total`, `pass_rate`. Quote evidence; a claim in the transcript that
  > the outputs do not bear out is a FAIL.
- **Review** — generate the viewer with `--previous-workspace <iteration-(N-1)>` when one
  exists. With a browser: run it as a server (`nohup python3 <sc>/eval-viewer/generate_review.py
  <iteration> --skill-name <target> --benchmark <iteration>/benchmark.json &`) and open it —
  in the Claude desktop app, in the Browser pane. Without one: `--static
  <iteration>/review.html` and give the path. Then **stop** and tell the user what they are
  looking at and that "Submit All Reviews" writes `feedback.json`. Read `feedback.json` (the
  server writes it into the iteration; the static page downloads it — copy it in) before
  anything else happens. Kill the server when done.
- **When skill-creator is missing** — `eval_workspace.py locate-skill-creator` exits 1.
  Then: the grader is a general-purpose subagent given the grading rules inline (PASS needs
  quoted evidence of genuine completion; superficial or unverified is FAIL); pass rates are
  computed by hand into `benchmark.md`; there is no viewer — the per-assertion table and the
  output paths go in chat for review. The log says "graded inline — skill-creator not found".
- **Record** — invoke `log-eval` with the set file, eval IDs, iteration directory, baseline
  ref and both pass rates, before reporting results. `evals/workspace/` is never committed;
  the set and the log are.

### `skills/run-evals/references/eval-kinds.md`

Headings, in order: `# Eval kinds`, `## The kinds`, `## Baselines`, `## Harness rules`,
`## Cost`. Under `## The kinds`, exactly these five lines start a numbered list (the
`headings` claim parses them), each followed by its method:

```
1. **mechanical** — …
2. **load** — …
3. **behavioral** — …
4. **trigger** — …
5. **platform-fact** — …
```

- mechanical: a script or `check-contracts`; no model. Pass/fail is the exit code. Examples:
  a file exists, frontmatter parses, `eval_workspace.py validate`, a planted defect fails.
- load: the plugin loads from its working copy and the new pieces register:
  `claude --plugin-dir <plugin> -p "List the skills and agents you have from <plugin>"`,
  pass when every new name appears. One `claude -p` call.
- behavioral: the loop in `SKILL.md`. Pass bar comes from the phase note (default: every
  expectation passes for `with_skill`, and its pass rate ≥ the baseline's).
- trigger: "Phase 2 adds this kind." — one line only, until phase 2.
- platform-fact: a fact the Claude Code docs do not settle, run once, in phase 0 of a plan,
  with the assumed answer written down first; later phases may not depend on it until
  logged.

`## Baselines` — `none` / `previous` / a ref, as in the SKILL.md schema, plus: an agent is
run by giving a general-purpose subagent its prompt file as instructions; its `tools:` and
`skills:` preloads are not reproduced, so a behavioral result about tool use says "proxy".
`## Harness rules` — the four executor bullets, as the rules they are. `## Cost` — the table
from the overview's approved proposal (mechanical: seconds; load: one `claude -p`, ~10k
tokens; behavioral: prompts × 2 + a grader each, ~0.8M tokens for 3 prompts, ~0.4M warm;
trigger: phase 2).

## Deviations

- **The planted `smoke` defect cannot fail the `headings` claim.** Step 4 said to add
  `` `smoke` `` to SKILL.md's kinds list and watch "run-evals names every eval kind
  eval-kinds.md defines" FAIL. It stayed PASS: in `contract_sweep.py` a reader's `cites` is a
  literal list in `contracts.yml`, never read from the reader file, and a reader `span` only
  parses capitalised `**Bold**` names — lowercase backticked kinds are invisible to both. The
  claim was added as specified; it guards the owner side (unbolding `**platform-fact**` in
  `eval-kinds.md` made it FAIL, exit 1) but not the reader side. Making it guard SKILL.md
  needs a change to the shared `contract_sweep.py` (a reader form that parses backticked
  names in a span), which is outside this note. Phase 3's `headings` claim has the same
  limit.
- **`eval_workspace.py` gained two subcommands beyond the table**, both found by P1-B1:
  `finalize <iteration>` (the grader copies `timing` into `grading.json`, which hides
  `timing.json`'s tokens from `aggregate_benchmark`) and `review <iteration> …` (skill-creator's
  viewer inlines outputs with `json.dumps` unescaped, so an HTML output containing
  `</script>` rendered the served viewer empty; `review` runs it unmodified with `</`
  escaped). SKILL.md's loop step 5 and **Review** section use them; `skill-creator.md`
  records both defects, plus that `aggregate_benchmark`'s delta is inverted against
  `old_skill`.
- **The grader prompt gained one sentence** for P1-B1: grade expectations naming `chat.md`
  against the final message at the end of `transcript.md`. The set's expectations name a
  `chat.md` that the verbatim executor prompt never asks for. The set was not edited (this
  note validates it only); fixing the wording is left for the set's next edit, with the
  grader's critique listed in `evals/2026-09-19-run-evals-first-loop.md`.
- **README's skills count** "Seven skills" became "Eight skills" alongside the new row.
- **`skill-creator.md` search order** also checks `~/.claude/skills/skill-creator` (a
  user-level skill), between the marketplace checkout and the desktop copy; E0.1 found none
  there.
