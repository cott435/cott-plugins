# 04 — run-phase runs evals and stops for review

Phase 4. `run-phase` runs a note's `## Evals` table through `run-evals`, stops for the user's
review whenever a row is behavioral, fixes and reruns once when a pass bar is missed, and
still runs notes written before 0.9 (no `## Evals` section) the old way. `log-eval` gains the
fields that link a record to its set and iteration. A toy plugin under
`evals/fixtures/toy-plugin/` gives `run-phase` something to be tested on. The gap it closes:
`run-phase` says every eval is "run and recorded" and nothing about how, and never stops for
a person to look.

Read the ledger's Notes for this phase first: E0.5 (phase 1) settled whether an executor
subagent can run `run-phase` (which fans out further). If it cannot, P4-B1/B2 run
`run-phase` in the main chat against the fixture copy, following the harness sheets by hand,
and the log says so.

## Decisions

- **Review gate:** after `run-evals` opens the viewer for a behavioral row, `run-phase`
  stops and says what to look at. It commits only after the user replies and
  `feedback.json` (if any) has been read. Feedback asking for a change within the note's
  Files is part of this phase; anything else is a *noticed:* line in the ledger.
- **One fix, one rerun.** A missed pass bar gets one fix inside the note's Files and one
  rerun as the next iteration, reviewed again. Still missed: a `## Deviations` entry (the
  bar, the result, what was tried) and the user decides whether to commit.
- **Compatibility:** a note with no `## Evals` heading runs the evals its Steps list names,
  exactly as before 0.9, and the ledger Notes cell says "old-format note".
- **Fixture branch naming** mirrors the real thing: plugin `toy`, slug `0.2`, branch
  `toy-0.2`.

## Specification

### `run-phase` — replaces the "Evals, logged first" bullet

- **Evals, through `run-evals`.** For each target in the note's `## Evals` table, invoke
  `run-evals` with that target's rows — the set file, the eval IDs, the baseline — in the
  table's order (platform facts and mechanical rows first). Every result is logged with
  `log-eval` before it is reported here, with the commit field reading *uncommitted — see
  working-tree diff*.
- **Stop for review.** When any row is behavioral, stop once the viewer is open (or the
  results table is in chat, if skill-creator is missing) and wait for the user. Read
  `feedback.json` before continuing. Nothing is committed before the user has replied.
- **One fix, then a Deviation.** A missed pass bar: one fix inside the note's Files, rerun
  that target's rows as the next iteration, review again. Still missed: append the outcome
  to `## Deviations` and ask whether to commit.
- **Notes written before 0.9** have no `## Evals` section; run the evals their Steps list
  names, as that list describes, and write "old-format note" in the ledger's Notes cell.

### `log-eval`

*What every entry records* gains, after **Tested against**:

- **Linked to its set** — for runs from `run-evals`: the set file and eval IDs, the
  iteration directory, the baseline (`none` or the ref), and the pass rate of each
  configuration; for trigger evals the rate before and after. A record that cannot be traced
  to a set cannot be rerun.

The template gains, under the `**Tested against:**` line:

```
**Set:** `evals/sets/<target>.json` evals <ids> · **Iteration:** `evals/workspace/<target>/iteration-<N>` · **Baseline:** <none | ref> · **Pass rate:** <with>% vs <baseline>% · **Trigger rate:** <before → after, trigger evals only>
```

And "It is not the automated skill-creator benchmark loop, which produces its own workspace
under a skill's `<skill-name>-workspace/`." becomes "Runs from `run-evals` are recorded here
like any other; their workspace stays in the gitignored `evals/workspace/`, and the entry
is what is committed."

### `templates/phases/progress.md`, Standing facts, 2nd bullet

"Every phase: edits → the plugin's own rules → `check-contracts` → `build-site` → the
phase's `## Evals` table run with `run-evals` (stopping for review when a row is behavioral)
and logged with `log-eval` → one commit `<plugin> <slug> (phase N): …` → this file, in that
commit."

## Deviations

- **Fixture `.gitignore`.** The note's tree for `evals/fixtures/toy-plugin/` lists no
  `.gitignore`; one was added with `evals/workspace/` and the `build-site` outputs, the
  lines `templates/.gitignore` gives every new plugin. Without it P4-B1's expectation
  "`evals/workspace/` does not appear in the commit" tests only whether `run-phase` stages
  by explicit path, and the toy's first `run-evals` would leave an untracked workspace that
  `run-phase`'s clean-tree check on the next phase would stop on.
- **P4-B1's discriminating half was missed, and not retried.** The bar reads "every
  expectation passes for `with_skill`; `old_skill` fails the review-gate expectation". The
  new `run-phase` passed 7/7 — and so did 0.8.0's. Its transcript names the two sources:
  the toy ledger's Standing facts ("behavioral rows stop for review", the wording
  `templates/phases/progress.md` now carries) and `run-evals`' own **Review** stop, added in
  phase 1. A note written in the 0.9 format therefore gets the gate whichever `run-phase`
  reads it; what the new bullets add is a gate that does not depend on the note's wording,
  plus the one-fix rule and old-format handling, none of which `evals/sets/run-phase.json`
  separates. The one allowed fix would have been to strip the review and `run-evals` wording
  out of the fixture's ledger and Steps — making the baseline fail by making the fixture
  unlike a real 0.9 plan — so on the user's decision at the review stop it was recorded here
  instead of retried. `evals/2026-09-19-run-phase-evals-and-review-gate.md` has the runs.
