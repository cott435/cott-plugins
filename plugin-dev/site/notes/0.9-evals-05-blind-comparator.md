# 05 — blind comparison (suggested)

Phase 5 — accepted suggestion. When a changed target's assertions cannot tell the new
version from the old (both pass everything, or the pass rates are within 10 points),
`run-evals` can ask skill-creator's comparator which output is better without telling it
which is which. Nothing in the core reads the result; removing this phase removes the
section, the subcommand and nothing else. The gap it closes: two good versions of a skill
look identical to assertions, and "is the new one actually better?" goes unanswered.

## Decisions

- **Reuses outputs.** Blind comparison runs on an iteration's existing `with_skill` and
  `old_skill` outputs — no new executor runs. Its cost is one comparator per eval.
- **When:** automatically for a changed target when every expectation passed in both
  configurations or the pass-rate difference is under 10 points; otherwise only when a note's
  Evals row says `blind`.
- **The key stays out of the prompt.** Which side is new is written to
  `eval-*/blind/key.json`, never passed to the comparator.

## Specification

- `blind <iteration-dir>`: for each `eval-*` with both configs, copies `with_skill/run-1/outputs`
  and the baseline's into `eval-*/blind/A` and `eval-*/blind/B` in a random order, writes
  `eval-*/blind/key.json` `{"A": "with_skill"|"old_skill", "B": …}`, prints the list of
  `{eval, a_dir, b_dir, prompt, expected_output}`. Exit 0.
- `## Blind comparison` states the trigger rule (Decisions), the command, the comparator
  prompt — "Read `<skill-creator>/agents/comparator.md` and follow it. Task: `<prompt>`.
  Expected: `<expected_output>`. Output A: `<a_dir>`. Output B: `<b_dir>`. Write
  `<eval dir>/blind/comparison.json` in the shape that file defines." — then un-blinding
  with `key.json`, the tally into `benchmark.md` under `## Blind comparison`, and the
  `**Blind:**` field in the log. Read `comparator.md` first; if its expected inputs differ
  from this prompt, follow the file and record the difference as a Deviation.

## Deviations

- **The comparator prompt uses `comparator.md`'s own input names.** The note's prompt was
  "Task: … Expected: … Output A: … Output B: …"; the file names its inputs
  `output_a_path`, `output_b_path`, `eval_prompt` and `expectations`, and generates its
  rubric from the task itself. The Specification says to follow the file where it differs,
  so `SKILL.md` **Blind comparison** passes those four names, adds the eval's
  `expectations` (which `comparator.md` accepts and scores as secondary evidence), and
  keeps the set's `expected_output` as context rather than as the only statement of the
  task.
- **`blind` prints `expectations` too**, not only `{eval, a_dir, b_dir, prompt,
  expected_output}` as the Specification listed — the prompt above needs them. It reads
  them from the iteration's `eval_metadata.json` (`assertions`) and `expected_output` from
  `evals/sets/<target>.json`, which is where it lives; outside a plugin root that field
  comes back empty and the rest still works.
- **The comparator is told to read nothing else under the iteration directory.** `key.json`
  is a sibling of `A` and `B`, so "the key stays out of the prompt" does not by itself stop
  a comparator from listing `blind/` and reading it.
- **`blind` exits 1 when no eval has both configurations** — the Specification's "Exit 0" is
  the normal path; an iteration with nothing to compare is an error worth a non-zero exit.
- **P5-B1's two sides differ in format**, `proposal.html` against `proposal.md`: 0.8 is the
  version that publishes a page. The comparator does not know which version is which, but
  the format tell is systematic across all three evals, so the three verdicts are not
  independent. Recorded in the eval log rather than worked around — the format *is* the
  change under comparison.
