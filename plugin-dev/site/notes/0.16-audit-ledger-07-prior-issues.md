# 07 — the prior-issues loop

Phase 07. A rerun's audit checks each prior fix instead of auditing from scratch:
`run-auditor` takes a `Prior issues:` input and writes one `P` line per issue; `audit-run`
decides per issue whether the fix was in the code that ran, widens the selection so each
issue's agent type and driver command is covered (`trace.py select --cover`), gives each
auditor the issues that apply to its piece, spot-checks every `held` and `recurred` at its
step, writes a Checks line per issue and the report's **Prior issues** table; `flow.py` marks
the chart. It closes the design's last gap, "the rerun audit is never told what was fixed".

## Decisions

- **Issues checked:** status `fixed`, `released` or `verified` (`I list --status
  fixed,released,verified --format json`), each with its latest attempt. `recurred` and
  `wontfix` are not re-checked; `open` has nothing to check. Reason: a recurred issue's fix
  failed; the next attempt is what gets checked.
- **Was the fix in the code that ran:** `index.json`'s `plugin_root`, when `git -C
  <plugin_root> rev-parse --git-dir` succeeds, by `git -C <plugin_root> merge-base
  --is-ancestor <commit> HEAD`; otherwise by version: testable when `fixed_in` is set and
  `index.json`'s `version` ≥ `fixed_in` (dotted-integer comparison). Not testable → a Checks
  line `not testable`, a row in the report, and no auditor sees it.
- **Once per session:** an issue with a Checks line for this `<id8>` is skipped on a re-pass
  (`--units new`). Reason: the design's warm-run rule.
- **Verdict per issue across auditors:** `recurred` if any auditor said so and the spot-check
  held; else `held` if any did; else `not exercised`. The Checks line cites the auditor's
  step. Reason: one line per audit per issue.
- **`select --cover` adds to any `--units` mode**, including a named list, and prints the
  segments to add on their own line. Reason: coverage is added to the normal selection
  (design, declined `--units issues`).
- **Issue marks are read from `<workspace>/../../../../audits/issues/`** when that exists
  (the workspace is `<plugin>/evals/workspace/audit/<id8>/`), else from `--issues DIR`.
  Reason: the plugin dir is four levels up by construction.
- **A recurrence's Found in line ends `<report path> P`**: its finding id is `P`, since it has
  no F finding, and it is not counted in **Totals**' `seen again` or the commit message's
  `<n> seen`; it is counted once, under `prior: … recurred`. Reason: the design's "never
  counted twice".
- **A `not testable` Checks line** has `—` for the unit and the step, and its evidence says
  why: `fix <commit> not an ancestor of <plugin_root> HEAD <sha>`, `fixed_in blank`, or `run
  version <v> below fixed_in <w>`. Reason: the next reader should not have to rerun the test.
- **The verdict words are owned by run-auditor** as a numbered bold list, so a `headings`
  claim can hold audit-run and fix-issues to them. `not testable` is audit-run's own word,
  defined there, since no auditor writes it.

## Specification

### `agents/run-auditor.md`

- **Inputs**, a new last bullet: `- **Prior issues**: `none`, or one indented continuation
  line per issue a rerun should show fixed in this piece, each `<ID> · attempt <n> · watch <applies_to> · held when
  <…> · recurred when <…>`. Decide for each whether this trace exercised that behavior, and
  what it shows.`
- New section, between **The checks** and **Severity and fault**:

```markdown
## Prior issues

When **Prior issues** is not `none`, after the checks write one line per issue given, in the
order given, under a `## Prior issues` heading after the last F finding:

`P · <ID> · <verdict> · <step id or —> — <evidence quoted short, or why it was not exercised>`

The verdict is one of:

1. **held** — the trace reached the behavior the issue's `held when` names and shows it. Cite
   the step. Never from the absence of a failure: a unit that never got there is not exercised.
2. **recurred** — the trace shows what `recurred when` names. Cite the step. Write the P line
   only, never also an F finding for the same fact, so it is not counted twice.
3. **not exercised** — this piece never reached that behavior. Say why in a few words, with
   `—` for the step, so the line reads `P · <ID> · not exercised · — — <why>`.
```

- **Findings file**: after the `## F2 · …` line of the example, add `## Prior issues` with one
  example P line, and the sentence: "The `## Prior issues` section is present only when the
  input carried prior issues."
- **Return**: `Findings: <n> ERROR, <n> WARN, <n> NOTE · prior <h> held, <r> recurred, <x> not
  exercised — <Findings path>`, then: "The `· prior …` part appears only when prior issues were
  given; with `Prior issues: none` the line is exactly as before."

### `trace.py select --cover`

`select DIR [--units HOW] [--cap N] [--cover a,b,…]` where each entry is `agent:<type>` or
`driver:<command>`. After the normal selection: for each `agent:<type>` with no selected unit
whose `role` or `type` matches, add the first finished unit of that type with reason `covers
agent:<type>`, within `--cap` (beyond it, print `over cap: …` and let the skill ask). Then
print `cover segments: seg-<n>[, …]` for every segment whose `command` begins
`/<plugin>:<command>` for a `driver:<command>` entry, and `uncovered: <entries>` for entries
no finished unit or segment matches. The summary line is unchanged.

### `skills/audit-run/SKILL.md`

- §3, after the selection: **Prior issues.** The issues to check (Decisions), the fix-ran test
  per issue, the once-per-session rule, then `T select … --cover <the applies_to entries of
  the testable issues>`; the cap of 12 and the question beyond it apply to the widened
  selection. Segments from `cover segments:` are audited in `driver` mode even when none of
  their units was selected. Show the issues as a table: id, attempt, testable (how), covered
  by.
- §4, the block's last field: `Prior issues: none`, or `Prior issues:` followed by one
  continuation line per testable issue whose `applies_to` names this unit's agent type, this
  segment's skill, or `cross`, each indented two spaces, in the form run-auditor's Inputs
  give. The field is always present.
- §5: a step **Verdicts** before **Issues**: parse each findings file's `## Prior issues`;
  spot-check every `held` and `recurred` at its step (the step must show what the Verify line
  says) and drop a failing one to `not exercised`, listed under **Dropped on spot-check**;
  combine per issue (Decisions); write `I check-result <ID> --attempt <n> --verdict <…>
  --session --version --date [--unit --step] --evidence`; for a `recurred` also `I seen <ID>
  …` with the same step, and file no new issue for it. **Prior issues** in the report is the
  table, one row per issue checked including `not testable`; **Totals** carries the counts.
  The commit message's `<n> checked` is the number of Checks lines written.
- §6 **Results** gains `prior: held <ids>, recurred <ids>, not exercised <ids>, not testable
  <ids>`.

### `flow.py` marks

For the session's `<id8>`: every issue whose Found in has a line `· <id8> ·` is marked
`found: <ID>` on that line's unit; every Checks line `· <id8> ·` with a unit is marked `<ID>
held` or `<ID> recurred` (the other verdicts are not drawn). Marks render as a second badge
line under the box's label (`✓ DT-003` green for held, `✗ DT-003` red for recurred, `+ DT-031`
grey for found) and as a **Issues** line in the unit page header linking to
`../../../../../audits/issues/<ID>.md` when that path exists. `trace.py flow DIR [--issues
DIR]` passes the directory through; `build` finds it the same way.

### `contracts.yml`

```yaml
  - name: audit-run and fix-issues use only the prior-issue verdicts run-auditor defines
    # run-auditor writes the P lines; its numbered list under "## Prior issues" is the one
    # list of held / recurred / not exercised. `not testable` is audit-run's own word for an
    # issue no auditor was given, and is defined there.
    owner: agents/run-auditor.md
    owner_span: ['## Prior issues', '## Severity and fault']
    readers:
      - file: skills/audit-run/SKILL.md
        cites: ['held', 'recurred', 'not exercised']
      - file: skills/fix-issues/SKILL.md
        cites: ['held', 'recurred']
```

## Deviations

- **The commit message says `(phase 7)`, not `(phase 07)`.** Step 8 wrote `(phase 07)`, which
  the ledger's `git log --grep='(phase 7)'` would not find (phase 5's note had the same slip).
- **`select --cover`'s output, where the note was silent.** With `--cover` given, the `cover
  segments:` line is always printed, as `cover segments: none` when no `driver:` entry matched,
  so audit-run can read it the same way every time; without `--cover` nothing changes. A
  `cross` entry is skipped by `select` (the cross auditor covers it). `over cap:` names each
  unit the cap kept out with its entry, `over cap: U03 (agent:reviewer)`.
- **An issue nothing in the run covers.** The note did not say what happens to a testable
  issue whose `applies_to` entries all come back `uncovered:`. audit-run §3 step 4 gives it to
  no auditor and §5 records it `not exercised`, evidence `no <entry> in this run`.
- **audit-run renders the chart a second time.** §5 runs `T flow <workspace>` once more after
  the Issues step, so the boxes carry this audit's marks (`flow.py` reads them from the
  ledger, which is written after the first render). The note specified the marks but not when
  audit-run redraws.
- **audit-run's last message names `/plugin-dev:fix-issues recurred`** when a prior issue
  recurred, beside `run:<id8>`. `audit-run.json` eval 6's last expectation asks for it; the
  note's §6 spec named only the Results line.
- **Boxes with marks are taller.** "A second badge line under the box's label" did not fit in
  the 54 px box, so when any unit in the run has a mark every box is 68 px and the marks sit on
  their own line; a run with no marks draws exactly as before. At most three marks are drawn
  per box, then `+n more`; the hover title lists them all.
- **B7.2 met its bar on the second iteration.** Iteration 5's with_skill run scored 11/13
  (its transcript summarised the auditor blocks and the `issues.py new` commands). The one fix
  was to the eval harness `ledger-prior-issues.md` (verbatim commands and auditor blocks, and
  general-purpose auditors from the plugin root, after a voided run had loaded the installed
  agent), plus one sentence in audit-run §5 step 4: a different finding matched to a recurred
  issue is an ordinary `seen`. Iteration 6: 14/14 vs old 0/14. `audit-run.json` eval 6's
  vacuous "no other issue file …" expectation now also requires a new issue file to exist.
