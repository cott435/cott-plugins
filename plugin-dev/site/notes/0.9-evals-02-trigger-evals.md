# 02 — trigger evals and the description optimizer

Phase 2. Fills in the `trigger` kind that phase 1 stubbed: for a skill the model invokes by
its description, measure how often it triggers on queries that should and should not invoke
it, with skill-creator's `run_eval.py`, and — the user's decision — optimize the description
with `run_loop.py` and apply the best one, under a guard that keeps the plugin's own scoping
rules intact. Then run it on plugin-dev's five automatic skills. The gap it closes: nothing
checks that an automatic skill fires when it should, or stays quiet in unrelated repos.

Read the ledger's Notes for this phase first: E0.2 (phase 1) settled how `run_eval.py`
handles a skill inside a plugin, and the **Mechanism** decision below depends on it.

## Decisions

- **Which skills get trigger evals:** only those the model can invoke by description — no
  `disable-model-invocation: true`, and not a knowledge skill that is only ever preloaded by
  an agent's `skills:` list. Typed skills are started by a person; their description is
  documentation, not a trigger.
- **Mechanism:** if E0.2 found `run_eval.py --skill-path <plugin>/skills/<name>` detects
  triggers directly, use that. If it did not, copy the skill directory into a temporary
  project's `.claude/skills/<name>/` and run `run_eval.py` from that project — the skill is
  then unnamespaced, which is what the script expects. Record which in
  `references/skill-creator.md`.
- **The guard:** every trigger set includes at least three should-not-trigger queries that
  are the same task *outside* a plugin repo (the scoping clause this plugin's `CLAUDE.md`
  requires in every description). A description from `run_loop` is applied only if (a) its
  held-out score beats the current one, (b) every one of those scoping queries still does
  not trigger, and (c) it still contains the phrase `only inside a plugin's own
  subdirectory`. Otherwise the current description stays, and the log says why.
- **Thresholds:** optimize only when the current held-out accuracy is below 0.9. Default
  `--max-iterations 5`, `--runs-per-query 3`, `--model` set to the session's model ID.
- **Applying** a description edits the skill's frontmatter in this phase's commit and is
  listed in the log with before/after text and scores.

## Specification

### `## Trigger evals` in `run-evals/SKILL.md`

States: which skills qualify (the Decisions bullet); the set file
`evals/sets/<target>.trigger.json` in skill-creator's format, a JSON list of
`{"query": "...", "should_trigger": true|false}`; how to write the queries (skill-creator's
guidance: realistic, specific, with paths and context; 8–10 should, 8–10 should-not, the
negatives near-misses rather than obviously unrelated); the guard, verbatim from Decisions;
the commands:

```
python3 -m scripts.run_eval --eval-set <set> --skill-path <skill dir> --runs-per-query 3 --model <session model>
python3 -m scripts.run_loop --eval-set <set> --skill-path <skill dir> --model <session model> --max-iterations 5 --verbose
```

(run from the skill-creator directory, in the background for `run_loop`, tailing its output
for progress); and that the result — rate before, rate after, the applied description or
the reason none was — goes to `log-eval` as `**Trigger rate:**`.

### `validate` for trigger sets

A file ending `.trigger.json` must be a list of objects with a non-empty string `query` and
a boolean `should_trigger`; at least 8 of each value; at least 3 should-not queries
mentioning a location or situation outside a plugin repo (heuristic: the query text does not
contain `plugin`, or says "not a plugin"). Problems print as in phase 1.

### The five sets

One per automatic skill: `log-eval`, `build-site`, `check-contracts`, `new-plugin`,
`run-evals`. Near-misses to include per skill, at least:

- `log-eval` — "write up the test results in the PR description" (should not), "record
  that the implementer agent passed the security trigger test in evals/" (should).
- `build-site` — "build the docs for my Python package with mkdocs" in a non-plugin repo
  (should not).
- `check-contracts` — "check the API contract tests in tests/contract/" (should not).
- `new-plugin` — "add a new skill to dev-team" (should not — that is not a new plugin).
- `run-evals` — "run pytest on the scraper" (should not); "does the documenter still write
  the Public names heading after my edit? test it" (should).

## Steps

1. Read E0.2's finding; choose the mechanism.
2. `eval_workspace.py` `validate` for trigger sets; then the SKILL.md section, eval-kinds.md
   line, skill-creator.md paragraph.
3. Write the five trigger sets; `validate` them.
4. For each skill: `run_eval` → if held-out accuracy < 0.9, `run_loop` → apply under the
   guard or keep. `run_loop` runs are long — run them in the background, one skill at a
   time, and log each before starting the next.
5. `check-contracts` (the `names_listed` and `headings` claims must still pass; an edited
   description is inside `skills/**`), `build-site`.
6. Commit: `plugin-dev 0.9-evals (phase 2): trigger evals and the guarded description optimizer`.

## Deviations

- **Mechanism: neither branch exactly as written.** E0.2 found `--skill-path
  <plugin>/skills/<name>` works directly — but only from a scratch project with its own
  `.claude/`, the plugin under test disabled there, and `--num-workers 1`. That is the
  mechanism chosen; nothing is copied into `.claude/skills/` (the script only reads the
  description from `--skill-path` and writes it as a temporary *command*, so a copied skill
  would just be a second competitor).
- **The commands are not run "from the skill-creator directory".** From there, the nearest
  ancestor with a `.claude/` is `~`, so `run_eval.py` would write its temporary command into
  `~/.claude/commands/`. Both commands in `run-evals/SKILL.md` **Trigger evals** run from the
  scratch project with `PYTHONPATH=<skill-creator>`, and add `--num-workers 1`; `run_loop`
  also gets `--report none` (its default opens a browser window) and `--results-dir
  evals/workspace/<target>/trigger`.
- **Guard (c) and the last Done-when bullet cannot hold as written.** Only `run-evals`'
  description contains `only inside a plugin's own subdirectory`. `log-eval` and
  `build-site` say "Use only in a plugin repo (one containing .claude-plugin/plugin.json)",
  `check-contracts` "Use only in a plugin repo that has a contracts.yml", and `new-plugin` —
  which runs from the marketplace root, not a plugin's subdirectory — has no scoping clause.
  The guard in SKILL.md is stated as "still contains the current description's scoping
  clause — for a skill that has it, the phrase `only inside a plugin's own subdirectory`".
  Adding the phrase to the other four was not done: a description edit here happens only
  through the optimizer under the guard.
- **"Held-out accuracy" before optimizing is `run_eval`'s full-set accuracy.** There is no
  held-out split until `run_loop` makes one (40%, its default); its iteration 1 re-measures
  the current description on that split, and guard (a) compares against that.
- **P2-T3 (`check-contracts`) needed a hand rewrite to meet its bar.** `run_loop`'s best
  (held-out 6/8 → 7/8) dropped "Use only in a plugin repo that has a contracts.yml", so
  guard (c) rejected it and the phase first closed at 0.70 against ≥ 0.85. At the user's
  request, that description was rewritten by hand with the clause restored, re-measured
  with `run_eval --description` (20/20; held-out 8/8 vs 6/8; no should-not triggered) and
  applied. The note only provides for applying the optimizer's own output; this was a hand
  rewrite, made at the user's request and held to the same guard.
- **Guard (b) was judged on the queries that are actually outside a plugin repo**, not on
  `validate`'s heuristic. For `run-evals`, the `log-eval` near-miss "log that the
  implementer eval passed in dev-team/evals…" has no `plugin` in its text, so the heuristic
  counts it as an outside query, but it names a plugin's `evals/`. It triggered with the
  applied description (3/3 in the after run); every real outside query stayed 0/3. Recorded
  in the log.
