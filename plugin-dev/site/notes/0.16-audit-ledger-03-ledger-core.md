# 03 — ledger core

Phase 03. The committed issue ledger's two formats and the one script that writes them:
`templates/audits/issue.md` and `templates/audits/run-report.md` are the one list of each
file's headings, and `scripts/issues.py` creates, updates, indexes, derives the status of and
checks issue files under `<plugin>/audits/`. Nothing uses them yet: phase 4 makes audit-run
write through them, phase 6 fix-issues and bump-version. It closes the design's "findings get
new numbers in every audit" gap by giving a finding an id that stays.

## Decisions

- **`issues.py` reads the plugin name from `<dir>/.claude-plugin/plugin.json`**; no
  `--plugin` flag. `--dir` defaults to the working directory. The ledger is `<dir>/audits/`,
  created on first write. Reason: one source for the prefix.
- **The template is read from the plugin bundle**, `Path(__file__).parent.parent /
  "templates/audits/issue.md"`, never copied into the plugin that holds the ledger. Reason: one
  list of the sections.
- **Attempt fields are `- key: value` bullets** under `### Attempt <n>`; `Verify` is one of
  them. Found in and Checks lines are `- ` bullets. Frontmatter is flat `key: value`. Reason:
  parsed by the standard library with three regexes.
- **`check-result --verdict held` without `--step` exits 1.** Reason: the design's never-claims.
- **`fix` without both `held when` and `recurred when` in `--verify` exits 1**, and without
  `--commit`. Reason: Verify is required and must name what a trace shows.
- **`stamp` checks ancestry when it can.** In a git checkout, an attempt is stamped only when
  `git -C <dir> merge-base --is-ancestor <commit> HEAD` succeeds; outside one, every `fixed`
  issue is stamped. Reason: a fix on an unmerged branch is not in the release.
- **Status precedence**: `wontfix` (latest attempt) → `open` (no attempt) → on the latest
  attempt: latest Check `recurred` → `recurred`; latest Check `held` → `verified`; `fixed_in`
  set → `released`; else `fixed`. A Check of `not exercised` or `not testable` changes
  nothing. Reason: the design's list, made total.
- **`list --format json`** gives the whole record so skills never parse issue files themselves.
- **`applies_to` spells a driver as `driver:<skill>`**, the typed skill's name without the
  plugin prefix (`driver:run-package`, `driver:ship`), an agent as `agent:<type>` with the
  prefix as the transcript records it or without (`agent:profiler` matches
  `dev-team:profiler`), and a cross finding as `cross`. Reason: `select --cover` matches a
  segment's command by that skill name.
- **`issues.py` validates `fault`, `severity` and `check` against the template's lists**, and
  exits 1 on any other value. Reason: the lists are the one place those words are defined.
- **A `commit` is the short sha** (`git rev-parse --short`); `issues.py` accepts 7–40 hex
  characters and resolves it through git for ancestry, never by string comparison. Reason:
  what a person reads in the index.
- **A `fixed` attempt has no `reason` bullet, and always a `- fixed_in:` bullet, empty until
  stamped** (no trailing space); a `wontfix` attempt has `status`, `reason` and nothing else.
  `stamp` fills the empty bullet and prints each id it stamped, one per line. Reason: one
  shape for `fix` to write and `stamp` and `check` to parse.
- **One-word plugin names take their first two letters, upper-cased** (`toy` → `TO`);
  hyphenated names take their initials (`dev-team` → `DT`, `plugin-dev` → `PD`,
  `a-b-c` → `ABC`).

## Specification

### `templates/audits/issue.md`

Verbatim (the `<…>` are what a writer fills):

```markdown
---
id: <PREFIX>-<nnn>
plugin: <plugin name>
title: <one line>
fault: <agent | driver | definition>
severity: <ERROR | WARN | NOTE>
check: <inputs | procedure | scope | hooks | claims | shape | waste | handoffs | agreement | shared state | repeats | rework>
applies_to: <comma-separated: agent:<type>, driver:<command>, cross>
rule_file: <path relative to the plugin root, or none>
rule_line: <line number at found_version, or none>
rule_quote: <the rule, quoted short, or none>
found_version: <plugin version that ran>
found_session: <id8>
found_date: <YYYY-MM-DD>
---

## Finding

<one or two sentences: what happened against what should have>

## Found in

- <date> · <id8> · <version> · <unit | seg-<n> | cross> · <step id> — "<evidence, one short quote>" · <report path> <finding id>

## Fix

### Attempt <n>
- status: <fixed | wontfix>
- reason: <wontfix only>
- branch: <branch>
- commit: <sha>
- files: <comma-separated paths>
- evals: <comma-separated eval log paths>
- fixed_in: <version; blank until bump-version stamps it>
- Verify: watch <applies_to>; held when <what a trace shows>; recurred when <what a trace shows>

## Checks

- <date> · <id8> · <version> · attempt <n> · <held | recurred | not exercised | not testable> · <unit | —> · <step id | —> — "<evidence, or why not>"
```

A new issue file is this template with the frontmatter filled, **Finding** and one **Found in**
line written, and **Fix** and **Checks** present with no entries. Writers: audit-run writes the
frontmatter, Finding, Found in and Checks; fix-issues writes Fix attempts; bump-version writes
only `fixed_in`. All through `issues.py`.

### `templates/audits/run-report.md`

Verbatim:

```markdown
# Audit · <P> <version> · <command(s)> · session <id8>

**Run:** <project> · <branch> · <span> · <models> · <n> units, <n> audited
**Rules checked against:** <plugin root> (<the version that ran | working tree — see note>)
**Flow chart:** `evals/workspace/audit/<id8>/flow.html` (gitignored; rebuilt with `/plugin-dev:run-flow <id8>`)
**Totals:** <n> ERROR · <n> WARN · <n> NOTE · issues: <n> new, <n> seen again · prior: <n> held, <n> recurred, <n> not exercised, <n> not testable

## Errors
### E1 · <issue id> (<new | seen>) · <fault> · <one-line finding>
<unit or segment> · evidence `<step>` · rule `<file:line>` · <still at HEAD | changed since <version>>
<two or three sentences: what happened, why it matters, and — for definition faults — the edit that would fix it>

## Warnings
### W1 · <issue id> (<new | seen>) · <fault> · <one-line finding>
<same shape, one short paragraph>

## Notes
- N1 · <issue id> (<new | seen>) · definition · <one line>
- N2 · — · <fault> · <one line>

## Prior issues
| Issue | Title | Attempt | Verdict | Unit · step | Evidence |
|---|---|---|---|---|---|

## Audited
| Unit | Type | Description | Verdict | E/W/N |
|---|---|---|---|---|

## Not audited
<units not selected and why, units still running, auditors that failed>

## Dropped on spot-check
<finding, and why its evidence did not hold — or "none">
```

Only `definition` NOTEs carry an issue id; other NOTEs carry `—`. With no prior issues the
**Prior issues** table has no rows and one line under it: `none: no issue had a fix in the
code that ran`.

### `scripts/issues.py`

`python3 ${CLAUDE_PLUGIN_ROOT}/scripts/issues.py <command> [--dir DIR] …`. Every writing
command re-renders `audits/INDEX.md` before it exits. Exit 0 on success, 1 with one line per
problem on stderr otherwise.

| Command | Arguments | Does |
|---|---|---|
| `new` | `--title --fault --severity --check --applies-to --rule-file --rule-line --rule-quote --found-version --found-session --found-date --finding` and the Found in fields `--unit --step --evidence --report --finding-id` | writes `audits/issues/<PREFIX>-<nnn>.md` with `nnn` = highest existing + 1 (`001` with none); prints the id |
| `candidates` | `--rule-file RF --fault F [--applies-to A]` | prints `<id> · <severity> · <status> · "<rule_quote>" · <title>` for every issue with that `rule_file` and `fault` (and an `applies_to` entry in common when given); `none` when there is none |
| `seen` | `<ID> --session --version --date --unit --step --evidence --report --finding-id` | appends a Found in line |
| `check-result` | `<ID> --attempt N --verdict V --session --version --date [--unit U] [--step S] --evidence` | appends a Checks line; `held` requires `--step` |
| `fix` | `<ID> --branch --commit --files --evals --verify` | appends `### Attempt <n>` with `status: fixed`; requires `--commit` and both `held when` and `recurred when` in `--verify` |
| `wontfix` | `<ID> --reason` | appends an attempt with `status: wontfix` and the reason |
| `stamp` | `--version V` | sets `fixed_in: V` on the latest attempt of every issue whose status is `fixed` (and, in a git checkout, whose commit is an ancestor of HEAD); prints the ids stamped, or `none` |
| `list` | `[--status s1,s2] [--applies-to A] [--session ID8] [--format json]` | one line per issue, `<id> · <status> · <severity> · <fault> · <applies_to> · <title>`, filtered; `--session` keeps issues with a Found in line for that id8; `--format json` prints the parsed records (frontmatter, finding, found_in, attempts, checks, status) |
| `status` | `<ID>` | prints the derived status |
| `index` | — | rewrites `audits/INDEX.md` |
| `check` | — | exits 1 naming each: a duplicate id; a file whose name is not its `id`; a missing section; a frontmatter key not in the template or one missing; a `held` Check with no step; a `fixed` attempt with no commit; `INDEX.md` differing from a fresh render. Else prints `ok: <n> issues` |

`audits/INDEX.md`:

```markdown
<!-- generated by issues.py — do not edit by hand; `issues.py index` rewrites it -->
# <plugin> · audit issues

| Id | Title | Fault | Severity | Status | Found | Seen | Fixed in | Last check |
|---|---|---|---|---|---|---|---|---|
| [DT-001](issues/DT-001.md) | … | definition | ERROR | open | 2026-10-07 ca48b249 | 1 | — | — |
```

Rows ordered by status `recurred`, `open`, `fixed`, `released`, `verified`, `wontfix`, then by
id. **Found** is `found_date found_session`; **Seen** the count of Found in lines; **Fixed in**
the latest attempt's `fixed_in` or `—`; **Last check** `<date> <verdict>` of the last Checks
line or `—`.

### `README.md`, **The rest of the bundle**

Two rows after `scripts/contract_sweep.py`:

- `| `scripts/issues.py` | The audit ledger: creates and updates issue files under a plugin's `audits/issues/`, derives each issue's status, renders `audits/INDEX.md`, and checks the ledger. `audit-run`, `fix-issues` and `bump-version` write through it; nothing writes an issue file by hand. |`
- `| `templates/audits/` | `issue.md` and `run-report.md`: the one list of an issue file's and a run report's sections. |`

## Steps

1. Write the two templates.
2. Write `scripts/issues.py`; run M3.1–M3.5 on a scratch ledger as you go.
3. The README rows.
4. The plugin's own rules; `check-contracts`; `build-site`.
5. Evals, logged with `log-eval`.
6. Commit: `plugin-dev 0.16-audit-ledger (phase 03): the audit ledger — issue and report templates, issues.py`.
