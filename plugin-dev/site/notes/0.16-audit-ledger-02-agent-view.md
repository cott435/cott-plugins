# 02 — agent view

Phase 02. `run-flow` learns to list every run of one agent type in time order, in one chat or
across several: `trace.py` gains `--sessions a,b` and `--branch <glob>`, `flow.py` writes
`agents/<type>.html` per session and `views/<type>-<date>.html` across sessions, and the skill
gains `--agent`. It closes the design's "nothing lists every run of one agent type" gap:
`/plugin-dev:run-flow ca48b249 --agent profiler` opens a page listing U01, U04, U06 and U08,
each one click from its full record.

## Decisions

- **`--sessions` and `--branch` require `--agent`** (design, Decisions taken, *planning*).
  Without it the skill prints `--sessions and --branch list one agent type across sessions:
  add --agent <type>` and builds nothing.
- **`--agent` matches the role or the full type**, case-insensitively: `profiler` matches
  `dev-team:profiler`; so does `dev-team:profiler`. Reason: people say the short name.
- **Every session's workspace is its own `audit/<id8>/`**, built or appended as in phase 1;
  the cross-session page is `evals/workspace/audit/views/<type>-<YYYY-MM-DD>.html` with the
  build date (local), overwritten by a later build the same day, each row linking to
  `../<id8>/units/U<nn>.html`. Reason: the design keeps the workspace path and puts
  cross-session views under `views/`.
- **`agents/<type>.html` is written for every type in a run** on every `write_html`, so a
  single-session `--agent` call only opens a page that already exists. Reason: the pages are
  cheap and the chart links to them.
- **The `Mode:` column** is the first line of the prompt matching `^Mode:\s*(.+)$`, else `—`.
  `trace.py build` stores it as `mode` on each `index.json` unit (additive). Reason: the view is
  rendered from `index.json` without opening every JSON.
- **The fixture's flow session gets its own id prefix and branch.** Today both planted sessions
  begin `0a0d17f0`, which is one `<id8>` workspace. The flow session becomes
  `0f10d17f-0000-4000-8000-0000000flow0` on branch `flow`; the planted session stays on
  `feature`. `evals/sets/audit-run.json` eval 3's prompt path changes with it. Reason: a
  cross-session view needs two workspaces.
- **`trace.py view` is a subcommand**, not more flags on `build`, so `build`'s arguments stay
  as they are (What must not break).

## Specification

### `trace.py`

- `sessions_for` adds `"branch"`: the first `gitBranch` seen in the session's main transcript,
  or `null`. `describe` prints it after the project.
- `build`: each `index.json` unit gains `"mode": <str or null>`.
- New subcommand: `trace.py view --plugin NAME --agent TYPE --root DIR (--sessions a,b |
  --branch GLOB)`:
  - `--sessions`: a comma list, each resolved as `build` resolves a session (id, prefix, path).
  - `--branch`: every session `sessions_for(NAME, include_headless=True)` returns whose
    `branch` matches GLOB by `fnmatch.fnmatchcase`. None matching: print `no session of NAME on
    a branch matching GLOB` and exit 1.
  - For each session, `build` into `DIR/<id8>/` (append when it exists). Then
    `flow.write_view(DIR, [workspaces], TYPE, today)`. Prints the view's path, then one line per
    session: `<id8> · <title> · <branch> · <n> units of TYPE`.
- `select`, `find`, `flow` and `build` keep their arguments.

### `flow.py`

- The agent view table, in both pages, has these columns in this order: **Session** · **Unit**
  · **Mode** · **Section** · **Round** · **Start** · **Duration** · **Tool calls** ·
  **Errors** · **Files written** · **Commits** · **Returned**. Rows are every unit whose
  `role` or `type` equals the agent type (case-insensitive), in `first_ts` order. **Unit** links
  to the unit page. **Returned** is `return_first_line`. **Session** is the `<id8>`, linking to
  that session's `flow.html`.
- `write_html(out)` writes `agents/<role>.html` for every distinct `role` in the run (the
  table above, with **Session** the same on every row), and links each from a `<h2>By agent
  type</h2>` list on `flow.html`.
- `write_view(root, workspaces, agent_type, date)` reads each workspace's `index.json` and
  writes `root/views/<agent_type>-<date>.html` with the table across all of them, unit links
  of the form `../<id8>/units/U<nn>.html`, and a header with one line per session: `<id8> ·
  <title> · <branch> · <n> runs of <type>`.

### `skills/run-flow/SKILL.md`

- `description`: after "…what it handed back." insert: "With --agent, every run of one agent
  type in time order, in one chat or, with --sessions or --branch, across several." Add to the
  trigger phrases: `"list every reviewer run on that branch"`, `"how many times did the
  profiler run, and what did each do?"`.
- `argument-hint`: `"[chat title words | session-id | latest] [--plugin NAME] [--agent TYPE] [--sessions a,b | --branch GLOB]"`.
- §1 step 2 gains: with `--sessions` or `--branch`, no positional session is read; `--agent` is
  required (the line in **Decisions**).
- §2: with `--agent` and one session, `T build` as before; with `--sessions` or `--branch`, `T
  view --plugin P --agent <type> --root <plugin dir>/evals/workspace/audit (--sessions … |
  --branch …)`.
- §3: the page served is `flow.html`, or `agents/<type>.html` with `--agent`, or, across
  sessions, `views/<type>-<date>.html` served from `evals/workspace/audit/`. With `--agent`
  the two closing lines are: the agent type, how many runs across which sessions (their
  `<id8>`s); and the URL, and that each row opens the run's page.

## Steps

1. `make_session.py`: the `FLOW` id and the flow session's `gitBranch`; update
   `evals/sets/audit-run.json` eval 3's prompt; run audit-run evals 3 and 4 (mechanical) to
   confirm nothing else moved.
2. `trace.py`: `branch` in `sessions_for`, `mode` in `build`, the `view` subcommand.
3. `flow.py`: the agent table, `agents/<role>.html`, `write_view`.
4. `SKILL.md`: description, argument-hint, the three flags.
5. `evals/sets/run-flow.trigger.json`: the two queries; `validate`.
6. The plugin's own rules; `check-contracts`; `build-site`.
7. Evals, logged with `log-eval`.
8. Commit: `plugin-dev 0.16-audit-ledger (phase 02): run-flow --agent — the agent view, in one session and across several`.
