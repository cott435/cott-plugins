# 03 — plan-phases specifies evals

Phase 3. `plan-phases` stops leaving evals to the next chat's imagination: it describes the
phase note section by section, gives every note a `## Evals` table whose kinds are
`run-evals`' kinds, writes the prompts and expectations of every behavioral eval into
`evals/sets/` in its phase-0 commit (the chat that understands the whole design writes the
tests, not the chat that builds one phase), and puts an eval budget in the proposal. It also
gets a worked example. The gap it closes: the template has one line for evals and
`plan-phases` never describes the template at all.

## Decisions

- **The example is the real thing.** `references/example-phase.md` does not copy a note —
  copies drift. It points at `${CLAUDE_PLUGIN_ROOT}/site/notes/0.9-evals-01-run-evals.md`
  (installed with the plugin) and annotates why each section is shaped as it is.
- **Sets are written in phase 0.** For a new target, a new `evals/sets/<target>.json`; for a
  changed one, evals appended with `added_in: "<slug> phase 0, run from phase N"`, and its
  existing evals rerun as regression in the phase that changes it. Harness sheets go under
  `evals/sets/files/<target>/`. Trigger sets are the exception: the phase that adds a
  model-invoked skill writes them (they are mechanical to generate and need the final
  description).
- **The table's Kind column** may hold only `run-evals`' five kinds, enforced by a
  `headings` claim (below).

## Specification

### `### The phase note` (new, under **What is written**, after the files table)

Lists the sections in order, one line each on what goes in it: the title `# NN — <name>`;
a purpose paragraph (what it adds, the gap it closes, written for a chat that has read only
the overview, the ledger and this note); `## Decisions`; `## Files` (a Path · Change
table); `## Specification` (exact frontmatter, headings, rules, contract entries, and any
prompt another model will be given, verbatim); `## Steps` (ordered so the bundle is
consistent after each); `## Evals` (the table below); `## Done when` (checkable without
judgment); and `## Deviations`, which `run-phase` appends and `plan-phases` never writes.
Ends: "`references/example-phase.md` walks through a real one."

### The eval rule in **Rules for the split** — replaces "Every phase has at least one eval…"

- Every phase has an `## Evals` table: `| ID | Kind | Target | Baseline | Set evals | Pass bar |`.
- Kind is one of `run-evals`' kinds — `mechanical`, `load`, `behavioral`, `trigger`,
  `platform-fact` — whose methods are in `run-evals/references/eval-kinds.md`; read it
  before choosing.
- A behavioral row names `evals/sets/<target>.json` and eval IDs; the prompts and
  expectations are written into that set in the phase-0 commit, with a harness sheet for any
  target that asks the user something.
- A phase that changes a target with an existing set reruns that set as regression, as its
  own row.
- The pass bar is checkable without judgment (default: every expectation passes and the
  target's pass rate ≥ the baseline's).
- Every phase touching a skill runs the plugin's rules, `check-contracts`, `build-site`,
  then its Evals table through `run-evals`.

## Deviations

- **The planted `smoke` defect cannot fail the `headings` claim** — the limit note 01's
  Deviations predicted. Step 2 said to plant `smoke` in plan-phases' kind list and confirm
  FAIL. With `` `smoke` `` added to the Kind bullet, `contract_sweep.py` stayed 4/4 PASS: a
  reader's `cites` is the literal list in `contracts.yml`, never read from the file. The
  claim was checked on the owner side instead: unbolding `**platform-fact**` in
  `eval-kinds.md` made it FAIL (exit 1) naming both readers, `skills/run-evals/SKILL.md` and
  `skills/plan-phases/SKILL.md`. Both files were restored and the sweep is 4/4 again.
  Guarding the reader side still needs a change to the shared `contract_sweep.py`.
- **Step 8 of `plan-phases` also changed.** The note rewrote step 6 to write the eval sets
  and left step 8 "rest unchanged"; step 8 committed "the notes and the ledger", which would
  have left the sets step 6 writes out of the phase-0 commit. It now reads "the notes, the
  eval sets and the ledger".
- **The trigger-set exception and `added_in` rule** from this note's Decisions went into
  the Kind/behavioral bullets of the new eval rule, since the Specification's bullet list
  did not carry them and a planner reading only `SKILL.md` would not otherwise know them.
- **The `### The phase note` section sits after the "Templates are at…" paragraph**, which
  belongs to the files table it follows.
- **The executor prompt gained one sentence**: where the target says `${CLAUDE_PLUGIN_ROOT}`,
  use the worktree's `plugin-dev/` for `with_skill` and the installed 0.8.0 cache for
  `old_skill`. Without it, `with_skill` would have read the installed 0.8.0 templates and
  never seen the new `## Evals` section P3-B2 tests. The installed 0.8.0 `phase.md` is
  identical to the baseline ref's (`bab28b8`).
- **P3-M1 failed as written, so `validate` was changed in this phase (the user's call).**
  `eval_workspace.py validate` rejected a set whose `target_path` did not exist. A set that
  `plan-phases` writes in phase 0 for a new target always hits this, because the target is
  created in a later phase. P3-B2's four sets failed only on that. `validate_set` gained
  `require_target`: `validate` now accepts a missing target and `init` still refuses one.
  `run-evals/SKILL.md` **The set** gained one sentence saying so. These are two files
  outside this note's Files table. P3-M1 was rerun and passed (exit 0). The committed sets
  still validate, and the negative cases still fail.
- **The graders' critique of `plan-phases.json` was not applied.** `run-evals`' loop step 7
  says to rewrite criticised expectations in the same change, but this note's Files table
  says the set is unchanged. The critique is listed in
  `evals/2026-09-19-plan-phases-evals-table.md` for the set's next edit.
- **Graders got the expectations by path**, the `assertions` list in each eval's
  `eval_metadata.json`, rather than inlined. Eval 4's graders were also told which output
