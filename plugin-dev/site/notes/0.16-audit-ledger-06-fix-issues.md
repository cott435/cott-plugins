# 06 — fix-issues

Phase 06. A typed skill that fixes ledger issues from any chat: it selects issues, plans one
edit per issue and gets one yes, edits on a worktree branch, runs `check-contracts`,
`build-site` and `run-evals` against the plugin's last tag, records a Fix attempt with a
`Verify:` line in each issue, commits, then proposes the merge and the bump. `bump-version`
gains the `fixed_in` stamp. `audit-run` now ends by naming the command to type. It closes the
"fixes from any chat" gap and gives phase 7's rerun audit something to check.

## Decisions

- **The branch is `<P>-audit-fixes-<YYYYMMDD>`** (suffix `-2`, `-3` when taken), created from
  `main` in a worktree at `<repo root>/../cott-plugins-worktrees/<P>_<branch>` with `git
  worktree add -b <branch> <path> main`. Reason: the root `CLAUDE.md`'s worktree rule and
  naming.
- **Two commits on the branch:** the edits (`<P> audit fixes: <ids> — <one line>`), then the
  attempts (`<P> audits: fix attempts for <ids>`). Reason: an attempt's `commit` must name the
  edit commit, which must exist first.
- **A set covers a file when its `target_path` is that file.** `run-evals` runs each covering
  set with the plugin's last tag as baseline (`git describe --tags --match '<P>-v*'
  --abbrev=0`, else `--match 'v*'`; with no tag at all, `previous`). A plugin with no
  covering set, or no `evals/sets/` at all, has nothing to run, and the skill says so rather
  than inventing a set. Reason: the design's "against the plugin's last tag", made total.
- **A Found in line whose report path does not exist** (the seed's, or a report from another
  checkout) is read as far as the issue file goes: the plan is made from **Finding**, the
  quote and the rule file, and the chat says the report was not found. Reason: fix-issues
  never stops on a missing record it does not need.
- **When the user declines the merge**, the skill says the branch and the worktree are left
  in place for them, names the bump level the merge would warrant, and stops; nothing is
  merged, removed or bumped. Reason: §7's two questions are independent.
- **The merge happens in the main checkout only when it is on `main` with a clean tree.**
  Otherwise the skill says so, leaves the branch and the worktree, and stops; the user merges.
  After a merge: `build-site` for **P** in the main checkout, then `git worktree remove`.
  Reason: the root `CLAUDE.md` on parallel chats and on rebuilding the site after a merge.
- **`wontfix` needs no edit, no checks and no eval**; it is recorded and committed with the
  attempts. Reason: nothing changed.
- **The plan's approval is one `AskUserQuestion`** with options `Approve the plan`
  (Recommended) and `Change it`; a changed plan is re-shown and asked again. The merge is a
  second question. Reason: design.

## Specification

### `skills/fix-issues/SKILL.md`

Component reference: `plugin-anatomy` `references/skills.md`. Frontmatter, verbatim:

```yaml
---
name: fix-issues
description: Fix the issues an audit filed in a plugin's committed ledger (audits/issues/) from any chat - select them by id, by run, or as open or recurred; plan one edit per issue and get a yes; make the edits on a worktree branch; run check-contracts, build-site and run-evals against the plugin's last tag; record a Fix attempt with a Verify line in each issue; then propose the merge to main and the bump. Use only inside a plugin's own subdirectory (one containing .claude-plugin/plugin.json) that has an audits/ directory. It never marks an issue verified - only an audit of a rerun can.
argument-hint: "[<ID> ... | run:<id8> | open | recurred]"
disable-model-invocation: true
---
```

Body headings in this order; `I` is `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/issues.py`:

- `# Fixing audited issues` — one paragraph: an audit writes what went wrong as issues with
  ids that stay; this skill is how they get fixed, from any chat, with the record of each fix
  in the issue so the next audit can check it.
- `## 1. The plugin and the selection` — **P** from `.claude-plugin/plugin.json`; stop without
  it, or without `audits/`. The selection: ids as given; `run:<id8>` is `I list --session
  <id8>`; `open` (the default) is `I list --status open,recurred`; `recurred` is `I list
  --status recurred`. Show it as a table: id, status, severity, fault, title. Nothing selected:
  say so and stop.
- `## 2. The plan, and your yes` — for each issue read its file (`I list --format json`), the
  run report each Found in line names, and the rule file in the working tree: `grep -F
  "<rule_quote>" <rule_file>` says whether the rule is still there. The plan is one proposed
  edit per issue: the file, the sentence or step that changes and how, or `wontfix` with the
  reason. For an `agent` fault: restate the rule where it applies, or add a guard where the
  plugin already guards that kind of action (a hook that checks it); otherwise `wontfix`
  with a reason. Ask once with `AskUserQuestion` (options above). No edit before the yes.
- `## 3. The worktree` — the branch and path in **Decisions**. Everything below runs in
  `<worktree>/<P>/`.
- `## 4. The edits` — the plan, as approved, and nothing else. Each is a change to an agent or
  skill like any other: read the component's `plugin-anatomy` reference first.
- `## 5. The checks` — the plugin's own rules (`CLAUDE.md`), `check-contracts`, `build-site`,
  then `run-evals` for every set under `evals/sets/*.json` whose `target_path` is a file the
  edits touched, with the last tag as the baseline. A failure goes back to §4. The eval logs
  `run-evals` writes through `log-eval` are the attempts' `evals`.
- `## 6. Record each attempt` — commit the edits. Then per issue `I fix <ID> --branch
  <branch> --commit <short sha> --files <paths> --evals <log paths> --verify "watch <applies_to>;
  held when <what a trace shows when the fix held>; recurred when <what a trace shows when it
  did not>"`, or `I wontfix <ID> --reason "<why>"`. `held when` and `recurred when` name
  something a trace shows: a return line, a tool call, a write. `I check` must print `ok`.
  Commit the attempts. Never `check-result`, never a `held`: only an audit of a rerun can.
- `## 7. Merge, then bump — each on its own yes` — ask to merge to `main`; on yes, the rule in
  **Decisions**. Then say a bump looks warranted, name the level (a fix to what an agent does
  is minor; wording is patch), and stop: `bump-version` runs only on a yes, and stamps
  `fixed_in` on the issues it releases.
- `## What this skill never does` — edit outside the worktree; merge, bump, tag or push
  without a yes; set an issue to verified; edit an issue file by hand; rerun the workflow.

## Steps

1. Write `skills/fix-issues/SKILL.md`; the README row and the `site.yml` line in the same
   step (the plugin's `CLAUDE.md` rule).
2. `bump-version` step 5; the README row.
3. `audit-run` §6 point 4.
4. `contracts.yml` readers. `check-contracts` PASS.
5. `build-site`.
6. Evals, logged with `log-eval`.
7. Commit: `plugin-dev 0.16-audit-ledger (phase 06): fix-issues, and bump-version stamps fixed_in`.

## Deviations

- **The README's `fix-issues` row.** The note gives it verbatim with the selection written
  `` (ids, `run:<id8>`, `open`, `recurred`) ``. `contracts.yml`'s `names_listed` claim reads
  every backticked lowercase word in **The skills** span as a skill name, so `open` and
  `recurred` failed it as "listed but no such directory". The row reads "(by id, by
  `run:<id8>`, or as open or recurred)" instead; the claim is unchanged.
- **The commit message** is `plugin-dev 0.16-audit-ledger (phase 6): …`, not `(phase 06)` as
  step 7 writes it: the ledger's SHA lookup greps `(phase 6)`, and phase 5 did the same.
- **The two template claims' names** in `contracts.yml` now name every reader
  (`audit-run, fix-issues and bump-version name only issue-file sections …`, `audit-run and
  fix-issues name only run-report sections …`), and the issue claim's comment no longer says
  readers arrive in phase 6.
