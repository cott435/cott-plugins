**Tested against:** uncommitted — see working-tree diff (`README.md`, `CLAUDE.md`, `CHANGELOG.md`, `site/workflows/*.md`, `skills/run-phase/SKILL.md`); the targets themselves as of `f688731` (`plan-phases`) and `2f256ed` (`run-phase`); baseline `plugin-dev-v0.8.0` → commit `bab28b8` · model: `claude-opus-5` (executors and graders; see Method for the fallbacks) · 2026-09-20
**Set:** `evals/sets/plan-phases.json` 1–4 · `evals/sets/run-phase.json` 1–2 · **Iteration:** `evals/workspace/plan-phases/iteration-3`, `evals/workspace/run-phase/iteration-2` · **Baseline:** `plugin-dev-v0.8.0` (`bab28b8`) · **Pass rate:** plan-phases 54/55 = 98.5% vs 47/55 = 73.5%; run-phase 12/12 = 100% vs 10/12 = 85.5%

## What was tested

P7-B1 and P7-B2 of `site/notes/0.9-evals-07-release.md`: on the finished branch, every
committed eval of both changed targets still passes against the released 0.8.0, and the
evals the plan added for the new behaviour separate the two versions. P7-M1 and P7-L1 are in
the companion entry `2026-09-20-release-checks-0.9.0.md`; P7-T1 in
`2026-09-20-trigger-rates-rerun.md`.

## Method

Real runs, through `run-evals`' own loop. `eval_workspace.py validate` on both sets, then
`init . <target> --baseline plugin-dev-v0.8.0` (an annotated tag; `rev-parse ^{commit}`
dereferences it to `bab28b8`, which is also `merge-base HEAD main`). Twelve executors as
general-purpose subagents with the verbatim executor prompt, then twelve graders with the
verbatim grader prompt over skill-creator's `agents/grader.md`, `finalize`, and
`aggregate_benchmark` per target. One run per configuration.

Three harness facts, carried forward from phases 1, 3 and 4 and needed again:
`${CLAUDE_PLUGIN_ROOT}` mapped explicitly — the worktree's `plugin-dev/` for `with_skill`,
the installed `0.8.0` cache for `old_skill`, since the baseline snapshot holds only
`SKILL.md` and 0.8.0's templates and references must come from a 0.8.0 bundle; "no browser,
write the page to `outputs/proposal.html`"; and, for `run-phase`, the temp-copy path given
explicitly. Cost: executors ~1.33M tokens, graders ~0.98M.

**Infrastructure fault, and what it cost.** Six executor runs terminated mid-flight on
`API Error: Opus 5's safeguards flagged this message … Details: [reasoning_extraction]`.
Five were `old_skill` plan-phases runs and one a `run-phase` `old_skill` run, which looked
like a configuration effect until `run-phase` eval 1 `with_skill` hit the same error on all
four of its own nested subagents and finished them on `claude-sonnet-4-5`: the fault tracks
long nested subagent runs, not the configuration or the subject matter (it hit the trading,
ML-papers and support-tickets prompts alike). The `run-phase` `old_skill` run was resumed in
place and had already completed its work; the four plan-phases `old_skill` runs were
relaunched from scratch on Opus and completed. **So the `old_skill` half of P7-B1 is
retried runs, not single-shot ones** — no grader saw a partial transcript (each relaunch
wrote its own, and the eval-2 relaunch moved the stale partial aside), but the comparison is
not as clean as the numbers alone suggest. Both `run-phase` `with_skill` runs ran their
nested executors and graders on Sonnet for the same reason, recorded in their own eval logs.

## Verdict

Both bars held. The change's actual content is visible in exactly two evals — `plan-phases`
4 (7/7 vs 0/7) and `run-phase` 1 (7/7 vs 5/7) — and everything else is regression cover that
0.8.0 also passes. That is the right shape for a release rerun, but it means neither
aggregate pass rate should be quoted as evidence that 0.9 is better.

**Phase 4's Deviation is only half-resolved.** The `run-phase` eval 1 grader confirmed the
review-stop assertion still cannot fail for a run that skips the gate on its own initiative:
the fixture's ledger Standing facts say "stopping for review when a row is behavioral" and
the note's Done-when says "reviewed", so an executor stops whichever skill it read. The
baseline failed that assertion here only on the incidental "viewer or results table" clause,
which is really a proxy for "run-evals ran". The fix is to the fixture — strip the review
language from `evals/fixtures/toy-plugin/site/notes/0.2-progress.md` and `0.2-01-farewell.md`,
or require `interview.md` to attribute the stop to the skill — and is not made here.

**One skill defect found and fixed.** Both `with_skill` `run-phase` executors independently
hit a contradiction between two of this plugin's own skills: `run-evals` step 7 says a weak
expectation the graders flag is rewritten in the set "in this change", while `run-phase`'s
"only this phase's edits" forbids touching a set outside the note's Files. Both resolved it
in `run-phase`'s favour and demoted the fix to a `*noticed:*` line. On the user's decision,
`run-phase/SKILL.md` now carries the exception explicitly (the eval sets this phase's own
`run-evals` run reads are in scope for expectation corrections, and the **Stop for review**
bullet says the same), and `check-contracts` and `build-site` were rerun after the edit.

**The graders' critique of both sets is recorded and not acted on**, deferred on the same
decision — see the *noticed:* lines in the ledger. The recurring kinds: assertions that pass
exactly when the thing they check never happened (`evals/workspace/ does not appear in the
commit`, "every harness file a set names was written"), one-directional chart/table checks,
five of sixteen `plan-phases` assertions being page boilerplate any templated page passes,
the `chat.md` gap recorded since phase 1 and still unfixed, and — the largest — nothing in
`run-phase.json` asserting that an old-format run *recorded* the note as old-format, which
is the one outcome eval 2 exists to probe.
