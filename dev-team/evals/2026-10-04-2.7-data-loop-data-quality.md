# 2.7-data-loop phase 3 — `data-quality`, how a section is designed and built from its data profile

**Tested against:** uncommitted — see working-tree diff (branch at `f58675a`; `skills/data-quality/SKILL.md` new, 79 lines) · model: Sonnet 5.5 (`sonnet`) for every executor and grader; mechanical and load rows run in the main thread (Opus 5.5), the load row's `claude -p` on Claude Code 2.1.283 · 2026-10-04
**Set:** `evals/sets/data-quality.json` evals 1, 2 (row 3.4) · **Iteration:** `evals/workspace/data-quality/iteration-1` · **Baseline:** none (`without_skill`) · **Pass rate:** 100% (23/23) vs 35% (8/23; eval 1 3/12, eval 2 5/11)

## What was tested

That a designer given `data-quality` turns a profile's verified kinds into a kinds table under
**Workflow / pipeline** with a treatment only where the user decided it, an `unclassified`
default, a reject record and one test per kind; and that an implementer given it builds one
handler per kind, keeps every rejected or altered row with its kind id as the reason, and
quarantines a failing row of no kind as `unclassified`. Plus the bundle checks: the contracts,
the size cap, and that the skill registers.

## Method

- **3.1** `contract_sweep.py` (plugin-dev 0.15.0), clean; then with the `├── data-quality/`
  line removed from `README.md`'s **Contents** tree, then restored.
- **3.2** `wc -l skills/data-quality/SKILL.md`.
- **3.3** from the repo root, `claude --plugin-dir ./dev-team -p "List the skills you have from dev-team"`.
- **3.4** `run-evals`' behavioral loop, one run per configuration. `with_skill` executors read
  `SKILL.md` first and followed it on the eval's prompt; `without_skill` executors got the
  prompt alone. One grader per run (skill-creator's `grader.md`); eval 2's graders ran
  `clean` on the sample themselves in a scratch copy. `S finalize`, `aggregate_benchmark`,
  static viewer. No blind comparison: the baseline is `none`.
- **Void and rerun.** Eval 2's first `without_skill` run read
  `dev-team/skills/data-quality/SKILL.md` (its step 2: "the design's Skills used"), so it was
  not a run without the skill; it graded 11/11. It was voided (kept outside the iteration, in
  the session scratchpad) and rerun once with one added harness line forbidding reads under
  `skills/data-quality/`. The rerun's result is the one recorded. No executor ended on an
  error.

Graders' critique of the expectations:

- Eval 1 #10 did not say what the reject reason must be, so a loose reading passed it. Corrected
  in the set: "the reject record's reason, which is the kind id (`K1` … `K5`)". The verdicts do
  not change (with_skill's cases assert kind `K1`…`K5`; without_skill already failed it), so no
  rerun.
- Eval 1 #11 "accepted rows stay accepted and unchanged": the with_skill design adds a `flag`
  key (`None`) to every output row, and its case reads "equal to the input but for `flag`
  `None`"; the grader passed it. Eval 2 #7 already pins "no key added" for the build. Left as is.
- Eval 1 #12 (`data-quality` under Skills used) cannot pass without the skill by construction;
  kept, it is the hand-off the implementer depends on.
- Eval 2 #2/#4/#6/#8/#9 pin the reject reason to the kind id or `unclassified`, which the
  rerun's grader called the skill's schema rather than cleaning behaviour; that schema is what
  the skill exists to fix, so they stay.
- Eval 2's rerun grader counted 17 rows in the sample; the file holds 18 (K1 3, K2–K6 2 each,
  accepted 5). The expectation stands.
- Not covered by any expectation: a row matching two kinds, a repaired row that then fails
  another check, rows missing fields. Both with_skill runs handle them (`unclassified`).

## Verdict

The claim holds. Rows 3.1 to 3.4 pass their bars. With the skill, both the design and the
build sort every row into accepted, a decided kind or `unclassified`, keep the reject record
by kind id, and honour the open D8; without it, the designer dropped K2's rows on an
undecided treatment and accepted the unverified K6, and the implementer lost the kind-id
reason and the `unclassified` default. One baseline run was voided for reading the target and
rerun; the set's eval 1 #10 was tightened without changing a verdict.
