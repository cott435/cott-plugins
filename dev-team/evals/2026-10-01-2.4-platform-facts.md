# 2.4 platform facts — what a `PreToolUse` event carries for Write and Edit

**Tested against:** Claude Code 2.1.283 (the platform; no plugin file is under test, branch `dev-team-2.4` at `f9a2827`) · `claude -p --model claude-sonnet-5-5` · 2026-10-01
**Set:** none — platform-fact row PF1 of `site/notes/2.4-00-overview.md` **Phase 0 evals** · **Baseline:** — · **Pass rate:** 1/1

## What was tested

**PF1** — the one fact `site/notes/2.4-design.md` lists as assumed: a `PreToolUse` event for
Write carries `tool_input.file_path` and `tool_input.content` (the whole new text), and one for
Edit carries `tool_input.file_path`, `tool_input.old_string` and `tool_input.new_string`.
Phase 4's suppression-comment refusal in `hooks/guard_writes.py` reads the new text from these
keys.

## Method

One real headless session, as the overview's PF1 row describes. A scratch directory outside the
repo (the session scratchpad, `…/scratchpad/pf1`, `git init`ed) with a project
`.claude/settings.json`:

```json
{"hooks":{"PreToolUse":[{"matcher":"Write|Edit","hooks":[{"type":"command",
  "command":"sh -c 'cat >> <scratch>/events.jsonl; echo >> <scratch>/events.jsonl'"}]}]}}
```

Then, from that directory:

```
claude -p "Use the Write tool to create a.txt in the current directory containing exactly: one
Then use the Edit tool to change one to two in a.txt. Do nothing else." \
  --model claude-sonnet-5-5 --permission-mode acceptEdits --allowedTools "Write Edit Read" < /dev/null
```

The two recorded events were parsed with `json.loads`. One session, two events; cost one short
Sonnet session.

Two notes on running it. The first attempt put the prompt after `--allowedTools`, which is
variadic and swallowed it (`Error: Input must be provided …`); the prompt goes first. And
Claude Code 2.1.283 printed `"claude-sonnet-5-5" isn't described by this version's model
catalog` with `[claude-code:unrecognized_model]`, then ran the session on that ID: the warning
is about the context window it assumes, not a refusal.

## Results

Top-level keys of both events: `cwd`, `effort`, `hook_event_name`, `permission_mode`,
`prompt_id`, `scratchpad_dir`, `session_id`, `tool_input`, `tool_name`, `tool_use_id`,
`transcript_path`.

| Case | Expected | Observed `tool_input` | Pass |
|---|---|---|---|
| Write `a.txt` = `one` | `file_path`, `content` (the whole new text) | `{"file_path": "<scratch>/a.txt", "content": "one"}` | yes |
| Edit `one` → `two` | `file_path`, `old_string`, `new_string` | `{"file_path": "<scratch>/a.txt", "old_string": "one", "new_string": "two", "replace_all": false}` | yes |

The file read `two` afterwards.

## Verdict

Holds. Every assumed key is present with the assumed meaning; Edit also carries
`replace_all` (a boolean). For Edit, `new_string` is the replacement fragment only, not the
file's whole new text, so a guard that refuses an *added* suppression comment reads
`new_string` (and may compare it with `old_string`), never a whole-file view. Phase 4's
refusal is built as planned.
