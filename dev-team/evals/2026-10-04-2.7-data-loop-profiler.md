## What was tested

That `dev-team:profiler` exists, registers, and is guarded as the note specifies (rows 1.1–1.5); and
that, given `agents/profiler.md`, a `Mode: profile` round-0 run writes a profile by the template's
twelve headings with the planted kinds counted against their checks and a `pending verify` round
line, and that a `Mode: verify` run rejects a check that catches good rows with only a
`revise: K<n>` line, or verifies every kind and raises a stub for each `repair` and `drop` kind
(row 1.6).

## Method

Rows 1.1–1.5: shell runs from `dev-team/`. 1.1 `contract_sweep.py`, then the step-4 planted defect
(`**Unexplained**` renamed `**Unsorted**` in `data-profile.md`), rerun, restored. 1.2
`python3 evals/fixtures/hook-events/check.py`. 1.3 `git diff --numstat dev-team-v2.6.0` on the two
budgeted files and `git diff --quiet dev-team-v2.6.0 --` on the eight existing agents. 1.4
`claude --plugin-dir ./dev-team -p "List the agents you have from dev-team"`. 1.5 needs an
interactive `/hooks`; none was available.

Row 1.6 is a **proxy**: each executor is a general-purpose subagent given `agents/profiler.md` and
the spawn block `status.py --profile` would print, not a spawned `dev-team:profiler`. Its tools
list, the write guard and the decisions sync hook are not reproduced (so no `D<n>` is assigned in
eval 3). Each eval's seed is built by `evals/sets/files/profiler/build.py case-<id>` into a
`mktemp -d` copy, and `build.py collect` copies what changed into `outputs/`. One run per
configuration, six executors, one grader each (skill-creator's `agents/grader.md`). The
executors were spawned in the first chat of this phase; their completion notices stayed there,
so iteration 1 has no `timing.json` and its benchmark's time and token rows read 0. No run errored.

Iteration 2, after the user chose option (a) at the review stop:

- **Set correction.** Eval 1 #4 and #6 now accept a denominator the profile explains (300 for a
  neighbour check that sets the 6 exact copies aside).
- **One fix to the agent.** In `agents/profiler.md` **Mode: verify** step 3, the return now
  names, for each rejected kind, one row its check misjudged, by its key columns, and the rule
  it is judged by.
- **Reruns.** Evals 1 and 2 `with_skill` were rerun as `iteration-2` (timing recorded: eval 1
  110,136 tokens / 186 s, eval 2 94,637 tokens / 60 s). The `without_skill` runs were copied in
  from iteration 1, their expectation text updated and no verdict changed. Eval 3 was not rerun,
  since the fix touches only the rejection path.
- **Second correction.** The iteration-2 grader called eval 1 #4 over-literal: the run added a
  check C13 over 296 rows (distinct rows with a price above zero), and its rule says so. #4 was
  reworded to "the number of rows the check reads when its rule or a line under the table says
  which rows it leaves out", and that one expectation was regraded (pass) with no rerun.

## Verdict

Rows 1.1–1.4 hold, and 1.5 was not run (headless). Row 1.6's bar is missed after the one fix.
Iteration 2 has 26/27 with_skill against 17/27 without, so with_skill ≥ without_skill holds but
"every expectation passes" does not.

- **The fix worked.** Eval 2 #5 now passes: the verify run's return names
  `trade_id 500044 (BOLT, seq 15 …) equal to the ts of the row before it` and cites the
  contract's rule.
- **The remaining miss is a flip, not a regression.** Eval 2 #6 passed in iteration 1 and
  fails in iteration 2, on similar narration. Every grader across both iterations says it can
  be checked only from the executor's own account of its sample.
- **Not caught by the set.** In iteration 2's eval 1, K3 and K4 are `quarantine; D?`. The
  verify mode makes `quarantine` read `no decision needed`, but the template's profile-mode
  wording ("`D?` (or `no decision needed`)") does not say which, and #5 accepts either.

Recorded as a Deviation in `site/notes/2.7-data-loop-01-profiler.md`. Committed on the
user's choice, with the miss standing.
