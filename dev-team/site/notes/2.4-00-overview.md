# dev-team 2.4 — overview

Branch: `dev-team-2.4`. Release at the end: `2.4.0` (MINOR), proposed to `bump-version` in
the last phase. Nothing here bumps or tags anything. Date: 2026-10-01.

This is the index of the phase notes. Each numbered note after this one is one phase, done
in the order listed under **Phases**, one chat and one commit each, by plugin-dev's
`run-phase` (typed with the slug `2.4`, from `dev-team/`). Nothing in a later phase is
required by an earlier one, so the branch is mergeable at any phase boundary.

The why, the workflows and their charts, the decisions and the non-goals are in
`2.4-design.md`, approved before this was written. This note does not repeat them; it says
what the design turns into, file by file and phase by phase.

  2, 3 and 6).
- Fixtures: state cases 84 → about 114, hook events 155 → about 183, and a new
  `evals/fixtures/entry-point/` suite.
- No skill is added or removed, so the two-file rule in this plugin's `CLAUDE.md` does not

Phases 1 and 2 may pair in one chat, one commit each. No other pairing: phases 4, 6 and 8 are
each at the upper edge of one chat.

**Why this order.** The design's build order has twelve steps and spreads each agent file and
the driver over several of them. The split groups by file instead, so each agent's eval set
and the driver's run once (the design's proof bar costs one run per phase that edits the
target). Scripts and hooks come first and stay backward compatible with the 2.3 wording; the
agents and the driver follow the mechanics they describe. Two consequences, both accepted when
the split was approved:

- The driver's gate-BLOCKED ask lands in phase 9. From phase 2 on `status.py` already shows
  the BLOCKED row and a two-command `next:` line.
- Phase 5 (the gate's checks) runs before phase 6 (the implementer), so no agent text names a
  check that does not exist yet. Between the two, a README with a grouped name cell fails its
  gate with a FAIL line that states the rule.

## Eval conventions for every phase

- **Baseline.** Every behavioral row's baseline is the tag `dev-team-v2.3.0`. The design chose
  it so one run also proves commit `1e81553`'s edits, which no agent was ever run against.
- **Model.** Every `run-evals` agent runs on Claude Sonnet 5.5, executors included; a headless
  session passes `--model claude-sonnet-5-5`.
- **Regression rows** (a set's existing evals): pass when `with_skill`'s pass rate over those
  evals is at least `old_skill`'s, and no expectation that passes in `old_skill` fails in
  `with_skill`. Existing evals carry `baseline: previous`; a regression row overrides it with
  `eval_workspace.py init --baseline dev-team-v2.3.0`.
- **Expectations revised in phase 0.** Where 2.4 removes on purpose what an existing
  expectation asked for, the expectation was rewritten and its eval carries a `note_2_4`:
  implementer evals 9, 11 and 12, and tester eval 1. No eval was removed.
- **New rows** (evals added in phase 0): pass when every expectation passes in `with_skill`
  and at least one fails in `old_skill`.
- **Baseline reuse.** When an earlier phase's iteration of the same set still exists under
  `evals/workspace/<target>/` on this machine, a later phase reuses its `old_skill` runs for
  the same eval IDs, regraded, and says so in its log. Otherwise it reruns them.
- **Hook scripts** are proven by hook-event cases, per the design's proof bar. The behavioral
  set `evals/sets/hooks.json` is not rerun in this plan; its target, `hooks/hooks.json`,
  changes only its `description`.
- **Byte sizes.** A phase that edits `agents/tester.md`, `agents/reviewer.md` or
  `agents/implementer.md` records the file's byte size before and after in its eval log.
- **No end-to-end eval.** `evals/sets/run-package.json` eval 4 is not run in any phase.

## Breaking changes to list in `CHANGELOG.md`

From the design's **What must not break**; phase 10 copies them with what to do.

1. A section whose implementer blocked or was let through now shows BLOCKED with `gate …`
   evidence, and `/dev-team:run-package` asks about it. Answer the question, or type the
   `next:` line.
2. A package shipped under 2.3 whose surface check fails prints `shipped: no (surface check
   FAIL)`. Run `status.py --surface <pkg>` and correct the README rows it names: one exported
   name per row.
3. A README with grouped or dotted name cells fails its section's next gate. The same
   correction, in that section.
4. A 2.2-or-later ledger entry still `open` re-opens its step even though its document was
   committed since. Run `/dev-team:run-package <pkg>`; if it was in fact answered, set its
   `Status:` to `resolved` by hand.
5. A re-probe that only adds to a shared probe doc no longer sends built consumers back to
   DESIGN. Nothing to do.
6. A repo with `docs/brief.md` and no `docs/architecture.md` now has the write and Bash guards
   on. Nothing to do; a refusal names the rule.
7. An implementer's return no longer lists test or lint results. Read
   `.dev-team/gate/<pkg>/<section>.txt`.
8. A tester stops with `spec-change:design` on a test case the repo's lint forbids, where it
   used to rewrite the case. Nothing to do; the designer rewrites the case in the next batch.
