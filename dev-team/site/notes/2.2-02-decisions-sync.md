# 02 — decisions-sync

Phase 2. Adds the two small scripts that make parallel implementers safe on the files they
cannot avoid sharing: `locked.py`, the one way an implementer touches `pyproject.toml`,
`uv.lock` or `.gitignore`, and `sync_decisions.py`, the `PostToolUse` hook that folds a
section's decisions inbox into `docs/decisions.md` under a lock and numbers `D?` stubs. With
them come the inbox's template, its `contracts.yml` claim, the hook's registration, and the
recorded hook-events cases that prove each path. The design's decisions-ledger chart is this
phase: the inbox written by the designer and implementer (phases 6 and 7) has its reader before
anyone writes it. The gap it closes: today two agents that stop for a decision in one batch
both pick "the next free `D<n>`".

## Decisions

- **`locked.py` waits up to 600 s, polling every 0.2 s, and removes a lock directory whose
  mtime is older than 600 s before retaking it.** Reason: the design says "stale after 10
  min" and names no wait; the wait equals the staleness so a crashed holder costs one wait at
  most. Exit 75 (`EX_TEMPFAIL`) on a wait that runs out, with the lock path on stderr.
- **`sync_decisions.py` waits up to 60 s for `.dev-team/locks/decisions/`** with the same
  staleness rule. Reason: a hook has a 600 s budget but a merge takes milliseconds; a minute of
  waiting means something is wrong, and the run gate catches an unsynced inbox anyway.
- **A numbered inbox entry whose number the central ledger lacks, or whose question differs
  from the central `D<n>`'s, is treated as a stub and renumbered.** Reason: the template forbids
  self-numbering, so this path is a defect route, and losing a question silently is the failure
  the hook exists to prevent. The `additionalContext` says `D14 → D15 (renumbered: not the
  central D14)`.
- **`Applied:` lines are inserted after the central entry's last `Applied:` line**, else at
  the entry's end. Reason: the implementer's own rule ("`Applied:` accumulates one line per
  section") reads as a block.
- **The hook creates `docs/decisions.md` with the line `# Decisions` when it has something to
  append and the file is missing.** Reason: the architect creates it only when it stubs; a
  designer stopping first would otherwise merge into nothing.
- **`--all` takes no lock event and prints one line per change**; it is what the run gate's
  FAIL message names. Reason: the design's repair path.
- **The inbox headings claim lists every reader now**, though the designer and implementer
  cite the fields only from phases 6 and 7: both files already contain the words `Scope`,
  `Raised by`, `Recommendation`, `Assumption if unanswered`, `Status` and `Applied`. Reason:
  one edit to `contracts.yml`, and the claim holds at every boundary.

## Specification

### `skills/status/scripts/locked.py`

```
Usage:  python3 locked.py <name> -- <command> [args…]
```

Docstring: "Run one command while holding `.dev-team/locks/<name>/` in the current directory,
a mkdir lock. Agents run in parallel and two of them editing `pyproject.toml`, `uv.lock` or the
root `.gitignore` at once lose one another's lines; this is the one way an implementer touches
those files (implementer.md, **Files outside your section**). `<name>` is `[a-z0-9-]+` —
`deps` for `uv add`, `gitignore` for the `.gitignore` block. Waits up to 600 s polling every
0.2 s; a lock older than 600 s is a crashed holder's and is removed. Exits with the command's
exit code; 2 on usage; 75 when the wait runs out. The command inherits stdin, stdout and
stderr and runs in the current directory. `guard_bash.py` lets a command through when its
program is this script."

Behavior: `os.mkdir(lock)` in a loop (`FileExistsError` → check mtime → sleep); `mkdir -p` of
`.dev-team/locks/` first; `subprocess.run(cmd)` with no shell; `finally: rmdir(lock)`. Nothing
else. No dependency beyond the standard library.

### `hooks/sync_decisions.py`

Docstring, verbatim in substance:

> PostToolUse hook on Write|Edit: fold a section's decisions inbox into `docs/decisions.md`.
>
> Input: the hook JSON on stdin (`cwd`, `tool_input.file_path`). Exit 0 unless
> `<cwd>/docs/architecture.md` exists and the path, made relative to `cwd`, matches
> `docs/packages/*/decisions/*.md`. Any role or the main thread may have written it.
>
> Under `.dev-team/locks/decisions/` (mkdir; wait ≤ 60 s; a lock older than 600 s is removed),
> read the whole inbox and the central ledger, then, entry by entry in file order:
> - `## D? — <question>`: the next free number (one more than the highest `## D<n>` in the
>   central ledger, counting numbers assigned earlier in this run); append the entry whole to
>   the central ledger with the heading renumbered; rewrite the inbox heading to `## D<n> —
>   <question>`.
> - `## D<n>` or `## D<n> — <question>` whose `n` exists centrally and whose question, when
>   given, equals the central one (whitespace-normalized): copy each `Applied:` line the
>   central entry lacks (exact line match, stripped) after its last `Applied:` line, else at its
>   end. Nothing else flows: `Decision:`, `Status:`, `Recommendation:` in the inbox are ignored.
> - `## D<n>` whose `n` is absent centrally, or whose question differs: a stub; renumber as above.
>
> Idempotent: a second run merges nothing. Creates `docs/decisions.md` (`# Decisions`) when it
> is missing and there is something to append. On any change, prints JSON on stdout:
> `{"hookSpecificOutput": {"hookEventName": "PostToolUse", "additionalContext": "dev-team
> decisions: <one clause per change, `; `-joined>"}}` — clauses `D? → D14`, `D14 → D15
> (renumbered: not the central D14)`, `D7: 1 Applied: line added`. No change: no stdout.
> Always exit 0; any error is reported on stderr (`dev-team decisions sync: error — …`) and
> the inbox is left as it was.
>
> By hand, `python3 sync_decisions.py --all` from the repo root merges every inbox the same
> way, prints one line per change, and exits 0 — the repair `status.py --run-gate` names when
> a session without the hook (an interactive `claude --agent`, a harness that dropped it) left
> an inbox unsynced.

The parsers: `status.inbox_entries` (phase 1) for the inbox; the central ledger is split on
`^## D(?=\d)` as `status.decisions()` does, keeping each entry's raw text for rewriting. Import
`status` exactly as `gate_on_stop.py` does (`CLAUDE_PLUGIN_ROOT`, `sys.dont_write_bytecode`).

### `hooks/hooks.json`

Add to `PostToolUse`, after the format hook's entry, a second object:

```json
{
  "matcher": "Write|Edit",
  "hooks": [
    { "type": "command", "command": "python3", "args": ["${CLAUDE_PLUGIN_ROOT}/hooks/sync_decisions.py"], "timeout": 60 }
  ]
}
```

`description` becomes: "dev-team: ruff after every .py edit by the implementer or tester; a
stop gate the implementer must pass; a per-role write guard; the decisions inbox folded into
docs/decisions.md after every inbox write. Every script exits 0 outside a repo that has
docs/architecture.md."

### `skills/planning-templates/references/decisions-inbox.md`

```markdown
# `docs/packages/<pkg>/decisions/<section>.md` — the decisions inbox

One file per section, written by that section's designer (stubs) and implementer (`Applied:`
lines) with the Write and Edit tools, never by shell, and read by `hooks/sync_decisions.py`,
which folds every entry into `docs/decisions.md` under a lock and numbers the stubs, and by
`status.py --run-gate`, which fails on an entry the central ledger does not hold. No two agents
write one inbox; nobody but the hook, the user, the driver, `pair` and the architect writes
`docs/decisions.md`. A new file starts with the line `# Decisions — <pkg>/<section>`.

Two kinds of entry, appended, each `## `-headed:

A **stub** — `## D? — <question>`, the `?` literal; the hook rewrites it to `## D<n> —
<question>` and the writer reads the number back before citing it. Then these lines, in order:

1. **Scope** — `<pkg>/<section>`, or the list of sections the question binds.
2. **Raised by** — the design's `OQ-<pkg>-<section>-<k>`.
3. **Recommendation** — one line.
4. **Assumption if unanswered** — what the design assumes; empty only when nothing honest fits.
5. **Status** — `open`. Nothing else.

An **applied** entry — `## D<n>`, the number of a central entry, then one or more:

6. **Applied** — `<pkg>/<section>, <date>, <path>`, one line per application.

Never in an inbox: a `Decision:` line; a `Status:` other than `open`; a number the writer chose
itself (`## D14 — …` for a new question — the hook renumbers it and says so); an edit to an
entry after the hook numbered it, other than an `Applied:` line. Only `Applied:` lines and new
stubs flow to `docs/decisions.md`; a `Decision:` or `Status:` written here never does.
```

`planning-templates/SKILL.md` table gains the row
`| an entry in `docs/packages/<pkg>/decisions/<section>.md` — a decision stub or an `Applied:` line | `references/decisions-inbox.md` |`
(the other rows' paths change in phase 5).

### `contracts.yml`

Under `headings:`, after the change-file claim:

```yaml
  - name: decisions inbox fields its readers parse are ones planning-templates defines
    # The designer writes stubs and the implementer `Applied:` lines into the inbox; the sync
    # hook parses both by field name and copies `Applied:` lines only, and the run gate fails on
    # an entry the central ledger lacks. A renamed field is a stub the hook merges without its
    # assumption, or an `Applied:` line that never reaches the ledger.
    owner: skills/planning-templates/references/decisions-inbox.md
    owner_span: ['1. **Scope**', null]
    readers:
      - file: agents/designer.md
        cites: ['Scope', 'Raised by', 'Recommendation', 'Assumption if unanswered', 'Status']
      - file: agents/implementer.md
        cites: ['Applied']
      - file: hooks/sync_decisions.py
        cites: ['Applied', 'Status']
```
