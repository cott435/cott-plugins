# 07 — the designer and the architect

Phase 07. The two agents that answer a wrong document, and the lines the design document
gains. Since phase 3 an entry stays open until its `Status:` is `resolved`, and the evidence
lists every open heading; this phase makes the designer and the architect take several
headings and close each one they answer (open item 2). The design gains three kinds of line
that other agents were inferring or could not know: which upstream packages the section
consumes (item 9), which entry points it owns (item 1), and which open decisions bind it
(item 5). `status.py` reads the first of them, so the implementer's block, and from phase 9
the tester's and the reviewer's, name only the interfaces the section uses. The designer
also stops naming test cases a tester cannot write (item 8) and checks its error cases
against each other before committing (item 19). The architect stages from `git status`,
since its return has no file list to stage from (item 17).

## Decisions

- **The `Upstream packages:` line is the last line of §2.** `status.py` finds it by its key
  anywhere in the design, so the position is for readers.
- **A name on that line that is not in the Packages row's `depends on` is ignored.** The row
  says what the package may depend on; the line narrows it and cannot widen it.
- **The designer's return gains two lines, `Resolved:` and `Left open:`,** and its cap goes
  from ten lines to twelve. The design requires an agent to name the entries it was handed
  and did not answer.
- **The closing check is its own procedure step,** between writing the design and committing
  it, so a run that skips it is visible in a trace.
- **`status.py`'s upstream change ships here,** with the design line it reads, and not with
  the driver in phase 9: `--inputs` is the implementer's block and needs no driver change.

## Specification

### `agents/designer.md`

**Hard rules, the first bullet.** "a `resolved` status on a `spec-change:design` entry your
rewrite answers" becomes "a `resolved` status on each `spec-change:design` entry you were
handed and your rewrite answers".

**Inputs, item 9:**

```
9. **Spec-change** — the open `spec-change:design` entries that re-opened this design
   (`delta` only), one per line, the first after the field's name and each further one on a
   line of its own below it: a ledger entry heading, or `<report path> — spec-change:design`
   when a review report raised it, whose **Spec-change** heading holds it. *May be `none`.*
```

**Modes, `delta`.** "Read the existing design at `Write to:`, the `own:` README, and the
change file or the spec-change" becomes "… and the change file or every spec-change you were
handed". The last three sentences of the bullet become:

```
  When `Spec-change:` names ledger entries, after writing the design set `Status:` to
  `resolved` and `Resolved by:` to `designer — <Run:>` on each entry the rewrite answers,
  with the Edit tool, one line each, in the file that holds it, and commit them with the
  design. An entry you were handed that the rewrite does not answer stays `open`, and your
  return names it: `status.py` keeps the section at DESIGN while any is open, so a `resolved`
  you did not earn hides the entry from every later run. Never set `resolved` on an entry you
  were not handed. A report-raised spec-change has no entry to close.
```

**Procedure.** Step 7 stays "Write the design document". A new step 8, and the old step 8
becomes 9:

```
8. **Check it against itself.** Every error case a §5 **Interfaces** row names has the
   exception type §6 **Error handling and logging** gives it, and every §7 case names a file
   and a value its §3 and §4 items use. Correct the design where they differ: a design that
   contradicts itself costs a tester stop, or ships as a silent deviation.
9. Commit, then return.
```

**Design document template.**

Item 2 gains, as its last sentences:

```
   Its last line is `Upstream packages: <pkg>, … | none`: the upstream packages whose
   `interface.md` this section consumes, by name. `status.py` reads that line, and the tester,
   the implementer and the reviewer are sent only those documents, so a package left off it is
   a document they never see.
```

Item 3 gains, after "which settings go in the section's `configs.py` per its §3.":

```
   An entry point the section owns — a line under `[project.entry-points."<group>"]` in the
   package `pyproject.toml`, such as a `pytest11` plugin or a migrations group — is one line
   of the plan, exactly `entry point: <group> <name> = <target>`, `<target>` a module or
   `module:attribute`, followed once by the words that it is registered through `locked.py`.
   The module `<target>` names is among the plan's files. The implementer adds the line with
   `entry_point.py` under the dependency lock, never by hand; a `[project.scripts]` command is
   the `surface` section's.
```

Item 7 gains, after "Name the fixture data each needs.":

```
   No case needs a subprocess, a skip, or a service that may be unreachable unless the case
   names its substitute: an in-process call, a fake built to the shipped signature, a
   recorded response. The repo's lint forbids `subprocess` in tests and the Guarded rule
   forbids a skip, so the tester stops on a case it cannot write as named.
```

Item 11 gains, after "so an unanswered question does not stop the implementer.":

```
   Then one line per `D<n>` whose `Scope:` covers this section (`repo`, `<pkg>` or
   `<pkg>/<section>`) and whose `Status:` is not `decided`: `D<n> binds this section: <the
   item it affects>`, or `D<n> binds <pkg>/<other section>, not this one`, or `D<n> binds this
   section (scope <scope>); no item affected`. The tester and the implementer read the line
   and do not infer it from `Scope:`.
```

The eleven item names, their numbers and their order do not change.

**Return.** "Ten lines or fewer." becomes "Twelve lines or fewer.", and the `done` block:

```
Result: done
Design: docs/packages/<pkg>/design/<section>.md
Open questions: OQ-<pkg>-<section>-1 (assumption: …), …  | none
Deviations: <count> under Contract deviations
Resolved: <entry headings set resolved this run> | none
Left open: <entry headings handed and not answered> | none
Commit: <sha>
```

`Resolved:` and `Left open:` are on every `done` return, `none` when no entry was handed.

### `status.py`

`design_upstream(pkg, section) -> list[str] | None`: the names on the design's `Upstream
packages:` line (`^\**Upstream packages:\**\s*(.*)$`, the first match; `none` gives `[]`);
`None` when there is no design or no such line.

`_upstream_interfaces(pkg, section) -> list[str]`: for each package of `upstream_packages(pkg)`
that `design_upstream` names, or every one when it returns `None`: `docs/packages/<dep>/
interface.md` when it exists, else `provisional: docs/packages/<dep>/contract.md`.

`implementer_inputs` uses it for **Upstream interfaces**. `spawn_fields` appends a fifth
line, `upstream interfaces: <paths, comma-separated> | none`.

The docstring: `--inputs` item 6 becomes "per package in the Packages row's `depends on`
that the design's `Upstream packages:` line names (every one when the design is missing or
has no such line)"; "`--fields <pkg>/<section>` prints … four `key: value` lines" becomes
"five", with item 5:

```
5. `upstream interfaces: <path>, … | none` — as **Upstream interfaces** in `--inputs`. The
   tester's and the reviewer's field; the designer is sent every upstream package.
```
