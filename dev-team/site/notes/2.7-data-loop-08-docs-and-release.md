# 08 — end to end, the docs, and the release proposal

Phase 8. Proves the whole loop on one marked section with real agents, checks the line budget
against 2.6.0 in one place, brings the user-facing documents up to what was built, and proposes
the release. It closes the plan: after it a reader of the README knows what a data stage is
before meeting one in a run, and `bump-version` has what it needs to decide.

## Decisions

- **The end-to-end run walks one section**, `/dev-team:run-package data clean`, on a seed whose
  `ingest` is already DONE. The loop under test is the profile loop around one build; building
  a second section would double the cost and add nothing.
- **Its baseline is the tag `dev-team-v2.6.0`**, not `previous`: on this branch `previous` is
  the same commit, and the tag stays right if the branch is rebased.
- **The line budget has no `contracts.yml` claim.** The four claim types (`forbid`, `headings`,
  `frontmatter`, `names_listed`) cannot count lines, so the budget is the script under
  **Evals**, run here and recorded in the eval log. The design asked for claims "where a claim
  type allows"; none does.
- **Minor, 2.7.0.** A new agent and a new skill; nothing a user of 2.6 will notice breaks.
  `bump-version` decides, on a yes.

## Specification

### `README.md`

- **Data-heavy sections** (new subsection, at most 30 lines), in this order: what gets marked
  and by whom (the architect, at PLAN, in the Sections table; the three marks); what happens
  before design (the profiler, checks over all the data, kinds, the verify run, which
  treatments you are asked about and which go ahead); what happens after the build (the round
  on the section's own output, new kinds reopen the design, two rounds then *one more round* or
  *defer*); where things live (`docs/sources/<token>.md`, `.profile.py`, `.sample.json` with up
  to five rows per kind; `.dev-team/data/<token>/`, not in git); how to re-profile by hand
  (`/dev-team:run-package <pkg> <section> --step PROBE`); and that a package with no `stage:`
  row runs exactly as before.
- The docs layout tree gains, after the `sources/<source>.stats.json` line:
  `├── sources/<token>.md · .profile.py · .sample.json   a DATA PROFILE of a stage: source, up to five rows per kind (profiler)`
- Every sentence that counts or lists the agents (grep `eight agents`, `researcher to`) names
  nine and includes the profiler's write scope: `docs/sources/`, `.dev-team/data/`, the
  ledgers, the inboxes, `docs/followups.md`.

### `site/flow.md`

- The node `PROBE["researcher ×P (probe)…"]` reads
  `PROBE["researcher ×P (probe) · profiler (a stage: source)<br/>sources with no entry yet; a built marked section"]`,
  with one new edge `REVIEW -->|"approved, marked section"| PROBE`.
- The sequence chart gains `Drv->>Pro: PROBE: status.py --profile block, verbatim` and the
  participant it needs.
- The files table gains a row for `docs/sources/<token>.md` (the design's files-table row,
  with the Stale-when cell as corrected in **Decisions taken**).

### `site/workflows/`

`new-repo.md` and `add-package.md` each gain one paragraph after the step that runs the
package: a section the architect marked `stage:` is profiled on real data before it is
designed and again after it is built; you are asked about each treatment that repairs or drops
rows; the pull cap is a decision with a default.
