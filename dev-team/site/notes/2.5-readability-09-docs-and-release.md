# 09 — end-to-end, docs and release

Phase 09. Every piece is in and each was proven alone. This phase proves them together, on
the case the design was written for: a package whose sections are all DONE and whose command
runs through a lambda, taken by `/dev-team:run-package` from the paths review through the FIX
it causes. Then it brings the documents a user reads up to what the plugin now does, writes
the changelog entry with its upgrade notes, and proposes the release in chat. It bumps and
tags nothing: `bump-version` does that, on a yes.

## Decisions

- **The release proposed is `2.5.0`, a minor bump.** `shipped:` changes meaning and a new
  gate check can fail a run, both of which a user notices; 2.4.0 changed `shipped:` the same
  way (the surface check) as a minor, and nothing a repo already holds stops being read.
  `bump-version` decides.
- **The end-to-end eval is graded up to the second paths review.** The fixture is a
  `state-cases` repo, whose designs are stubs, so a pass bar that needed every agent to
  finish cleanly would measure the fixture. What 2.5 adds is the order of events: the review
  before the close, the re-open, the FIX with the report, no close before an approval.
- **`paths-e2e` is a `state-cases` case** so the eval's seed is built the way the other driver
  evals' seeds are.
- **Eval 14 spawns this branch's agents.** Its executor spawns real `dev-team:<agent>` agents,
  which are whichever version the session has registered. Run this phase's chat with the
  plugin loaded from the working copy (`claude --plugin-dir ./dev-team`, the ledger's first
  standing fact), and before row 9.4 confirm it: the `dev-team:reviewer` the session lists has
  `Focus: paths` in its description. An installed 2.4.0 reviewer would fail the eval for a
  reason that is not the driver's.

## Specification

### `README.md`

**Reviews**, a new paragraph after the one that ends "The verdict is `approve`, `request
changes` or `spec-change`.":

```
Once every section is DONE, one more reviewer (`Focus: paths`) follows each command of the
package from `cli.py` to its external effects, on the call tree `status.py --paths <pkg>`
prints. It writes `docs/packages/<pkg>/reviews/paths/<date>-r<n>-p.md`, with one row per
command under **Paths**, and may block on four things only: a command more than 8 frames from
its first external effect (P1), a lambda, closure or mapping dispatch on a main path (P2), a
pipeline or orchestrator that fails the reader's test in `python-style-guide`'s
`references/pipelines.md` (P3), and a trivial single-use helper or options bag on a main path
(P4). Each finding names a section, and `status.py` re-opens that section as FIX n with the
paths report as its previous round. A package is not shipped until this review approves; at
round 3 the driver asks *one more round* or *defer*. A package with no `[project.scripts]`
commands needs no paths review.
```

The list of questions the driver asks (the bullets that start "**A section whose implementer
blocked**" and "**A package whose surface check fails**") gains:

```
- **A paths review that still requests changes at round 3** (`paths: round 3 (request changes:
  …) (cap)`): the driver quotes the line and offers *one more round*, which runs an
  implementer and a review for each section it names and then the paths review again, or
  *defer*, which moves the findings to `docs/followups.md`.
```

The knowledge-scope table's `python-style-guide` row: its first cell becomes
`` `python-style-guide` — inside a file: docstrings, function shape, pipelines, `__init__.py`, naming ``.

The three conventions: the **Docstrings on everything** bullet gains "A summary line says
what the function changes outside itself."; the **Function shape** bullet becomes:

```
- **Function shape.** Phases inside a function are fine, each with a one-line purpose comment;
  a helper is extracted only when the jump buys something. A limit is met with a seam: no
  `**options` bag, no packed tuple, no three-statement helper with one caller. Every call on a
  main path names its target, and a pipeline reads as its steps (`references/pipelines.md`).
```

The paragraph **Enforced, not intended.** gains: "The lint block caps positional parameters
(`PLR0917`; keyword-only ones are free) and requires ruff V or later. The stop gate also runs
`status.py --shape`: a run that adds a trivial single-use helper or an options bag does not
pass.", with V the number phase 01 wrote.

The upgrade notes (the list that holds "**A package shipped under 2.3 may now print**")
gains the five items of the overview's **Breaking changes to list in `CHANGELOG.md`**, each
as a bold lead and what to do.


### `site/workflows/`

- `new-repo.md`, where `/dev-team:run-package` closes a package: one paragraph saying the
  paths review runs once every section is DONE, what it may block on (the four items, one
  clause each), that its findings come back as FIX rounds, and that the close waits for
  `paths: approved`.
- `adopt-existing-repo.md`: one paragraph saying the stop gate's shape check judges only
  lines added since a section's `Mode: document` design was committed, so adopted code is
  measured and never failed; and that the first paths review of an adopted package usually
  finds P1 to P4 items and takes several FIX rounds.
- `change-shipped-code.md`: one sentence saying a paths report goes stale when any section's
  code changes, so the review runs again before the changed package is shipped.

### `CHANGELOG.md`

A new entry above `## [2.4.0]`:

```
## [Unreleased]

A package reads from its command down to its first external effect. From the `data` package
of `quant`, built under 2.3.0 with every review approved: 17 frames to the first download, 416
single-use helpers, 49 options bags. Design: `site/notes/2.5-readability-design.md`.
Evidence: the `2.5-*` logs in `evals/`.

### Changed

- The lint block caps positional parameters (`PLR0917`, `max-positional-args = 5`) instead of
  all of them, and requires ruff V or later (<phase 1 sha>)
- The stop gate runs `status.py --shape`: a run that adds a trivial single-use helper or an
  options bag fails, indirect calls and entry-point depth are recorded as `MEASURED`, and
  adopted code is never failed (<phase 2 sha>, <phase 5 sha>)
- `python-style-guide`: no options bag, main paths called by name, docstrings written from the
  caller's side, `log` for logging only, private class names unique among sections that call
  each other; new `references/pipelines.md` (<phase 3 sha>)
- `status.py --paths <pkg>` prints each command's call tree to its external effects
  (<phase 4 sha>)
- The reviewer gains `Focus: paths`, once per package when every section is DONE, with a
  closed blocking list P1 to P4; its findings re-open the sections they name, and a package is
  not shipped until it approves (<phase 6 sha>, <phase 7 sha>)
- The implementer meets a size limit with a seam and fixes a paths finding in its own section;
  the designer writes pipelines to the reader's test (<phase 8 sha>)

### Upgrading

<the five items of the overview's Breaking changes list, each as a bold lead and what to do>
```

with each `<phase N sha>` the short sha from the ledger and V the number.
