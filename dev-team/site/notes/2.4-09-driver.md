# 09 — the driver

Phase 09. Every rule the design changes for `skills/run-package/SKILL.md`, in one edit, and
the runner its evals need. Since phases 2, 3, 5 and 7 `status.py` prints rows the 2.3 driver
has no words for: a BLOCKED row with `gate …` evidence, an evidence cell that lists several
headings at PLAN and DESIGN, `shipped: no (surface check FAIL)`, and a fifth `--fields`
line. The driver also still says it branches on an agent's last hand-back, which it never
receives (open item 14). This phase makes it branch on the first hand-back and then on the
next rows; ask about a gate-BLOCKED row with the record in front of the user; send every
open heading to the designer and the architect (item 2); send the tester and the reviewer
only the upstream interfaces the design consumes (item 9); ask, and not close, when the
surface check fails (item 15); end with the Summary when the user answers a question in free
text (item 10); and print `uncommitted:` from git (2.2 ledger, phase 9). The runner and
post-processor of the driver evals were never committed in 2.2, so those evals could not be
repeated; this phase commits them.

## Decisions

- **One driver phase.** The design changes the driver in five build-order steps. Each costs
  a run of the headless set, so they are made together, after the scripts and agents they
  describe.
- **Evals 1, 2, 3, 5 and 6 run headless through the committed runner; evals 7 to 10 run in
  `run-evals`' ordinary executor loop.** Each of 7 to 10 turns on a question the driver asks,
  and a headless session has no `AskUserQuestion`: it goes straight to the Summary. In the
  executor loop the harness sheet answers. If eval 3, which also asks, cannot ask headless,
  it runs in the executor loop too and the log says so.
- **Evals 7 to 10 seed from state cases.** `evals/fixtures/state-cases/build.py <case>
  <dest>` builds the exact row each needs (`gate-blocked`, `design-spec-change-two-open`,
  `blocked-decision`, `shipped-surface-check-fail`); no new fixture tree. A state-case repo
  has no root `pyproject.toml`, so `status.py --scaffold` says `needed`; the four harness
  sheets tell the executor to take it as done. The baseline's plugin root is the 2.3.0
  snapshot, `status.py` included, so in evals 7, 8 and 10 the baseline never sees the 2.4 row
  and fails one step earlier than the 2.3 driver text would.
- **The runner lives at `evals/runners/run-package/`.** Not under `evals/sets/files/`, which
  executors may read, and not under `evals/workspace/`, which is ignored.
- **A granted *run the implementer again* or *review anyway* is held like a granted round:**
  in the driver's memory for this run, and not asked again.
- **The driver may Read one more file:** the gate record of a row it is asking about. It
  quotes lines from it; it does not judge them.

## Specification

### `skills/run-package/SKILL.md`

The frontmatter does not change: no argument is added, and the description stays true.

**D1 — What you never do.**

- The git bullet becomes: "Run a git command that writes. The only git you run is `git
  rev-parse --short HEAD`, at the start and at the end, `git rev-list --count <start>..HEAD`
  for the summary, and `git status --porcelain -- docs/decisions.md` for the summary's
  `uncommitted:` line."
- The bullet "Open the files the agents wrote to check their work" gains, in its list of
  what may be read: "and the gate record `.dev-team/gate/<pkg>/<section>.txt` of a row whose
  evidence starts `gate `, for the question you ask about it (**Asking**)".
- "Every other spawn field comes from `status.py --fields <pkg>/<section>`" stays.

**D2 — Spawning an agent, "Resolving values".** The sentences on upstream packages and on
`--fields` become:

```
Upstream packages are the `<pkg>` row's `depends on` in the Packages table: each is
`docs/packages/<dep>/interface.md` when that file exists, else `provisional:
docs/packages/<dep>/contract.md`. The designer is sent every one. The tester and the reviewer
are sent the `upstream interfaces:` line of `status.py --fields`, which holds only the
packages the section's design says it consumes (every one, when the design does not say), and
the implementer's block resolves it the same way. Sources are the row's `source` cell,
`<kind>:<token>` each. `status.py --fields <pkg>/<section>` prints five lines — `mode:`,
`change file:`, `design mode:`, `diff base:` and `upstream interfaces:` — run once per section
you spawn for, and each table below names the line a field copies.
```

**D3 — the role tables.**

- Designer, **Spec-change**: "every heading the row's evidence lists when it reads `open
  <heading>; <heading>; …` and names `spec-change:design`, one per line, the first after the
  field's name and each further one on a line of its own below it; else `none`".
- Designer, **Skills to invoke**: "the row's `builds with`; `none` when the cell is empty or
  `—`".
- Tester, **Upstream interfaces** and Reviewer, **Upstream interfaces**: "the `upstream
  interfaces:` line of `status.py --fields`".
- Designer, **Upstream interfaces** stays "per upstream package, as resolved above".
- Architect, **Spec-change**: "at PLAN only: every heading every PLAN row's evidence lists
  (`open <heading>; <heading>; …`), one per line. At the close the block ends after `Run:`".

No field name changes.

**D4 — Loop, steps 3 and 4.** Step 3: "A row granted *one more round* or *defer* this run is
not asked again" becomes "A row granted *one more round*, *defer*, *run the implementer
again* or *review anyway* this run is not asked again". Step 4's first sentence becomes "The
rows that count with `ready` `yes`, plus the rows granted a round, a defer, an implementer
run or a review." Its PLAN sentence becomes "the batch is one architect for the package,
with every open heading of every PLAN row in `Spec-change:`, and nothing else". Two bullets
gain a sentence:

- IMPLEMENT or FIX n: "A gate-BLOCKED row granted *run the implementer again* gets its
  implementer here."
- REVIEW: "A gate-BLOCKED row granted *review anyway* gets its reviewers here: two at round
  1, one `full` otherwise."

**D5 — Loop, step 5,** its first paragraph replaced:

```
5. **Branch** on each return's first line, `Result: <value>`, and read nothing past it except
   where a case below says so. A return is the agent's **first** hand-back: the hand-back tool
   delivers one report per run, and what an implementer does after it — a gate retry, a block,
   a third red attempt — never reaches you as a message. It reaches you as a row: the stop
   gate writes every stop to the section's record and `status.py` derives the row from it, so
   a section whose implementer handed back `done` and then blocked, or was let through, shows
   BLOCKED with `gate …` evidence at step 6, and step 3 asks. What a `done` return says after
   its first line is on disk, and the next `status.py` shows it; relaying it to the user is
   re-sampling the agent's summary.
```

and the `blocked` or `stopped` bullet becomes:

```
   - `blocked` or `stopped` → **Asking**, with the return as the question, whatever the next
     `status.py` shows. A block that comes after the hand-back is not this case: it has no
     return, and arrives as a gate-BLOCKED row.
```

**D6 — Loop, step 7:**

```
7. **Close.** When every section of the package is DONE and the `shipped:` line is not
   `shipped: no (surface check FAIL)`, the architect with `Package:` and `Run:` only — the
   close. A `<section>` walk skips this unless its section was the last one not DONE. On
   `shipped: no (surface check FAIL)` the close does not run: **Asking**. Then **Summary**.
```

**D7 — Asking.** Two bullets join the list of what stopped:

```
- a gate-BLOCKED row (evidence `gate blocked: …` or `gate let through after 3 attempts, …`):
  Read the section's record `.dev-team/gate/<pkg>/<section>.txt`; the question is the row,
  the record's `result:` line and its `FAIL` and `blocked:` lines, quoted as they stand, with
  *run the implementer again*, *review anyway* and *stop here* as the options;
- every section DONE and `shipped: no (surface check FAIL)`: run `status.py --surface <pkg>`;
  the question is its `FAIL` lines as printed, with *fixed, retry* and *stop here* as the
  options;
```

Three bullets join "Record the answer":

```
- For a gate-BLOCKED row, no ledger edit: *run the implementer again* grants the section an
  implementer, with the `--inputs` block as at IMPLEMENT; *review anyway* grants it its
  reviewers. Once a review round covers the code `status.py` stops reading the record, so the
  answer holds across re-runs.
- For the surface check, nothing: *fixed, retry* re-runs **Loop** step 2, and *stop here* is
  **Summary**. The close waits until the check passes.
- **An answer that is none of the options** — free text typed in place of a choice — ends the
  loop where it stands: go to **Summary**, with the row or the two lines you asked about as
  `stopped because`. Do not act on the text: no diagnosis of the plugin, no file this skill
  forbids you to read, no edit. The user reads the Summary and types what they want next.
```

The last paragraph ("No questions when `AskUserQuestion` is not available …") gains: "A
gate-BLOCKED row is quoted as it prints."

**D8 — Summary.** The `stopped because` line of the block becomes

```
stopped because: <the agent's first two lines, the row as it prints, the shipped: line, or the run gate's FAIL lines>
```

The block's first line reads `stopped at <section> BLOCKED` for a stop at a BLOCKED row and
`stopped at the surface check` for a stop at the surface question.

and in the paragraph under it, "`uncommitted` only when you edited `docs/decisions.md`"
becomes "`uncommitted` only when `git status --porcelain -- docs/decisions.md` prints a
line: an agent's commit may have carried your edit, and then nothing is uncommitted".

**D9 — the sentence after the loop.** "On `request changes`, nothing is spawned from the
verdict itself …" stays word for word: the claim `the review loop's exit is never bypassed by
a bare next command` reads it.

### `evals/runners/run-package/`

Rebuilt from the 2.2 ledger's description (phases 9 and 11); the originals lived in a session
scratchpad and are gone.

- **`run.sh <eval id> <with_skill|old_skill> <plugin dir> <run dir>`.** Makes a `mktemp -d`
  copy of the eval's seed as its harness sheet describes it; writes `.claude/settings.json`
  in the copy disabling the installed `dev-team` plugin, so only `<plugin dir>` is loaded;
  runs, from the copy, `claude -p "<the eval's prompt>" --plugin-dir <plugin dir> --model
  claude-sonnet-5-5 --permission-mode acceptEdits --allowedTools "<the tools the driver and
  its agents need>" --output-format stream-json --verbose`, writing `<run dir>/stream.jsonl`;
  then calls `post.py`. `<plugin dir>` is the working tree for `with_skill` and the
  iteration's `baseline-snapshot/` for `old_skill`.
- **`post.py <run dir> <repo copy>`.** Writes `<run dir>/outputs/` and `<run dir>/transcript.md`
  from `stream.jsonl` and the subagent transcripts beside it: every Agent call with its
  `subagent_type` and prompt, grouped into batches (one assistant message id is one batch);
  every Bash command the driver ran; the final message; `git log --format='%h %s'` of the
  copy; every `.dev-team/gate/**/*.txt`; and the last `status.py <pkg>` output. Nothing it
  writes holds an expectation.
- **`README.md`.** The two commands, what each output file is, and that the model each
  session ran on is read from the transcript's `model` field, not from the flag.

### `contracts.yml`

- `nothing counts on a hand-back after the first`: `files` becomes `['agents/*.md',
  'skills/**/*.md', 'hooks/*.py']`, and the comment's last sentence goes.
- `gate record lines and result values their readers parse are ones the gate writes`: a third

- `evidence forms the driver copies are ones status.py prints`: the reader's `cites` becomes

## Deviations

1. **`run.sh` passes more to `claude -p` than the note lists.** The note gives `--plugin-dir`,
   `--model`, `--permission-mode acceptEdits`, `--allowedTools` and the stream flags. A
   headless session has no `AskUserQuestion`, and evals 3, 5 and 6 need what the harness
   sheet says about questions and about where the walk ends. So `run.sh` also passes
   `--disallowedTools AskUserQuestion`, `--add-dir <run dir>/outputs` and
   `--append-system-prompt`. The appended prompt holds a stand-in that appends each question
   to `outputs/interview.md` and answers it, plus the sheet's **Answers** and **Where the walk
   ends** sections, copied verbatim. 2.2's runner did the same (2.2 ledger, phase 9). It
   holds no expectation. With it, eval 3 asked headless, so it did not move to the executor
   loop.
2. **The session loads a copy of `<plugin dir>`, not the working tree.** The note says
   `<plugin dir>` is the working tree for `with_skill`. Claude Code refuses a Write inside a
   `--plugin-dir` directory as "a sensitive file", and the working tree's `evals/workspace/`
   holds the run's `outputs/`. Eval 3 `with_skill`'s `interview.md` Write was refused that
   way, and the run was voided. `run.sh` now copies `<plugin dir>` without `evals/` (and
   without `site/docs/`) beside the fixture copy and loads that. `runner.json` names both the
   copy and its source. The eval 3 `with_skill` rerun used the copy; the runs before the fix loaded
   the directory directly, and none of them wrote inside it.
3. **`post.py` writes more than the note lists:** `returns.md`, `gates.md`, `gate-history/`
   (from `run.sh`'s watcher), `status-final.txt`, `driver-bash.md`, `git-oneline.txt` and
   `cost.json`, because the harness sheets of evals 1–6 ask for them under **After the run**.
   It also strips Claude Code's `[Subagent hand-back]` frame from a return before taking its
   first line. Without that, every return's "first line" is the frame. Found on the proof
   run and fixed before the other runs.
4. **Evals 7–10 ran headless,** as in phases 7 and 8: the run-evals executor prompt
   verbatim, in `claude -p --model claude-sonnet-5-5`, with `Skill`, `Agent` and
   `AskUserQuestion` withheld. The note says "executor loop". The protocol is the same; only
   the transport differs, and it keeps the chat's subagent spawns for graders and the
   comparator.
5. **The harness sheets name the old git set.** The sheets of evals 1, 2 and 3 still list
   `git rev-parse --short HEAD` and `git rev-list --count` as the driver's only git. D1 adds
   `git status --porcelain -- docs/decisions.md`. Eval 1 #6 was corrected (set, run-evals
   step 7). The sheets' driver-limits bullet was not: the runner does not pass it to the
   session, and editing it is not in this note's Files. It is a *noticed* line in the ledger.
