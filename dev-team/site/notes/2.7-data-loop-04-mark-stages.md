# 04 — marking the data stages

Phase 4. The package-contract template gains the source kind `stage`, so the architect, whose
own file does not change, marks a data-heavy section at PLAN: `stage:<token>` in the row's
`source` cell, `dev-team:data-quality` in `builds with`, and one **Package conventions** line
carrying the pull cap and its `D<n>`. `status.py --run-gate` fails a `stage:` row with an empty
`depends on`, because nothing would produce its data. Until this phase a row is marked by hand;
after it, `/dev-team:plan-package` proposes the marks where the user sees and edits them.

## Decisions

- **Six lines, in the `source` paragraph.** The template is read at every PLAN, so the text is
  the budget's whole share and goes nowhere else. What a profile is and how it is used stays in
  `data-profile.md` and `data-quality`.
- **The pull cap is asked through the ledger, with an assumption.** The architect already
  writes `D<n>` stubs; the template tells it this one carries a recommendation and an
  assumption, so an unanswered cap does not block and the user still approves vendor spend.
- **The run-gate check reads only `stage:` rows**, so a contract with none prints what 2.6.0
  prints.

## Specification

### `package-contract.md`

In item 2, the paragraph that starts `` `source` is each external source the section consumes ``
keeps every sentence. Its first sentence's list of kinds gains `stage`, in place: "`api` for a
service called over the network, `dataset` for a file, table or corpus that is read, `stage`
for data the section's own dependencies produce (below)". Then this paragraph is inserted after
it, six lines as wrapped here, blank line included:

```
   A section whose job is to clean, validate, reconcile or audit data its dependencies produce
   is marked: `stage:<token>` in `source` (the token names the data, `rawbars`, not the
   section), `dev-team:data-quality` in `builds with`, and one **Package conventions** line,
   `` `stage:<token>` — <what the data is>; lands at <path>; pull cap <n> <unit>, D<n> ``, the
   cap from the vendor probes' cost and quota headings, stubbed with an assumption. Never on a
   row with no `depends on`, and never on a section that only passes data through.
```

Net growth of the file at most 6 lines: the in-place edit must not add a line, and the inserted
paragraph's blank line counts.

### `status.py`

`run_gate`, after the contract-exists check, when `pkg` is given and its contract exists:

```python
for r in sections(pkg):
    stages = [t for k, t in _sources(r.get("source", "")) if k == "stage"]
    if stages and not _names(r.get("depends on", "")):
        fails.append(f"{pkg}/{r['section']}: stage:{stages[0]} has no depends on; nothing produces its data")
```

The module docstring's sentence on what `--run-gate` fails on gains: "and on a `stage:` row
whose `depends on` is empty". `skills/status/SKILL.md`'s `--run-gate` paragraph gains the same
reason.

## Deviations

- **The `stage` paragraph's blank line (step 4).** The note said: insert the paragraph after
  the `source` paragraph, "six lines as wrapped here, blank line included". The block as given
  is six lines of text, so with its blank line it is seven, one over the file's share of six.
  What was done: the paragraph's sentences are appended word for word to the end of the
  `source` paragraph, with no blank line between, and that paragraph is rewrapped at 98
  columns (the file's widest existing lines) so that no code span breaks across a line:
  15 lines where there were 9, net growth 6. Why: the line budget is a hard rule (overview,
  **Rules every phase follows**), and as its own paragraph the text needs seven lines at any
  width the file uses. No later note depends on the paragraph break.
- **Row 4.6's pass bar (step 6).** The bar: `with_skill`'s pass rate ≥ `old_skill`'s, and its
  contract holds no `stage:`, on eval 1, described as "a package contract with no data-heavy
  section". The result: 8/8 vs 8/8 (blind: the new version preferred), but `with_skill` marked
  `clean` `stage:rawtrades` with `dev-team:data-quality`, a conventions line and a pull-cap
  `D1`. Eval 1's brief (`evals/fixtures/two-package/`) gives `clean` the job "Drop exact
  duplicate rows and sort by `ts`" over the rows `ingest` reads, which the design's rule
  (**Mark the data stages**: a section whose job is to clean, validate, reconcile or audit data
  its dependencies produce) marks. What was tried: nothing; the one fix inside this note's
  Files would narrow the paragraph so that `clean` goes unmarked, which contradicts the design.
  Log: `evals/2026-10-04-2.7-data-loop-mark-stages.md`. Committed on the user's choice (a):
  the marking is correct per the design, and the bar's "no `stage:`" condition rested on a
  wrong premise about the fixture.
