# 08 — the tester and the reviewer

Phase 08. The two agents that judge a section from its documents. The tester's file still
carries five sentences twice, from the `1e81553` merge; they go first. Then its rules: it
reads documents and nothing else, so a fact only upstream source holds is not tested (open
items 8, 12); a design case the repo's lint or the no-skip rule forbids is a design defect,
not a rewritten test (item 8); a decision the design assigns to another section is a
`Not written:` line (item 5); its count is a bare count (items 4, 20); a defect stop reads
only its prompt's documents (item 11); and it preloads the skill three of five audited
testers never read (item 3, E5). The reviewer learns what the gate record now means: a
`blocked` record or a failing surface check is CRITICAL, since the section should not have
reached review (items 14, 15); a departure from the design with no ledger entry is CRITICAL
even when the design contradicts itself (item 19); and a wrapped `xfail(` is not a finding
(item 18). This is also the first run of the tester set against `1e81553`'s edits.

## Decisions

- **Two agents, one phase.** Neither edit depends on the other; each is one file and one
  set. 2.2 paired agents the same way.
- **A test file is removed with git: `git rm -- <file>` for a file a commit holds, `git
  clean -f -- <file>` for one this run wrote.** The design says `git rm`. In `new` mode, the
  case the design gives as its reason, the file was written by this run and is untracked,
  and `git rm` cannot see it. Both commands name one file under the tester's own tree; `rm`
  stays unused.
- **A per-section name-check failure is CRITICAL in any section,** not only a package-wide
  one on `surface`. The design says "a failing surface check"; the per-section check is the
  same check run earlier, and only that section's implementer may correct its README.
- **The gate-record item is a fifth entry of the closed CRITICAL list.** The list stays
  closed; "a mechanical failure is never yours" gains the one exception.
- **A let-through record stays a WARNING.** The design makes `blocked` CRITICAL and leaves
  the let-through rule as it is: the user chose *review anyway*, and the FAIL lines are
  quoted.
- **The tester's upstream-source rule has one exit per case:** a fact no document gives is a
  `Not written:` line, and one the fixtures cannot be built without is a `design-gap`.

### `agents/reviewer.md`

**R1 — The evidence, the opening paragraph.** "a header naming the section and the attempt,
one line per check, and a last `result:` line" becomes "a header naming the section and the
attempt, a `commit:` line, one line per check, and a last `result:` line. A record with no

**R2 — The evidence, the `FAIL` lines bullet,** replaced:

```
- **`FAIL` lines** are mechanical failures the gate already reported to the implementer. They
  are never a finding of yours, with the exceptions **Severity** item 5 names. When the
  `result:` line is `letting the run stop after 3 attempts …`, the user chose to have the
  section reviewed anyway: quote that line under **WARNING**, so the round's record shows the
  section was let through with failures. A record whose `result:` is `blocked` is different:
  the implementer said it could not finish, and the section should not have reached review.
  That is a CRITICAL quoting the record's `blocked:` line, whatever else you find.
```

and the section gains a last paragraph: "The implementer's return is not evidence: you are
never given it. A README sentence saying a check ran counts only when the record shows the
line."

**R3 — The evidence, the paragraph on `docs/constraints.md`,** gains: "An `xfail(` call a
formatter wrapped over several lines, its `D<n>` on a later line of the call, is not a
finding: the gate reads the call to its closing bracket."

**R4 — Severity.** The closed list gains:

```
5. A **gate record that holds the section** — the record's `result:` is `blocked`; or a `FAIL
   surface` line, on the `surface` section; or a `FAIL surface names` line, on any section.
   The package cannot ship while it stands, and only this section's implementer can correct
   what it names. The conformance reviewer raises it in round 1 and the `full` reviewer after;
   the correctness reviewer does not repeat it.
```

and "A mechanical failure is never yours at any severity (**The evidence**)." becomes "Any
other mechanical failure is never yours at any severity (**The evidence**)."

**R5 — Focus: conformance.** After "A `fail` row is a finding at the severity **Severity**
gives it." add "A `fail` row for a departure from the design is CRITICAL unless a ledger
entry covers it." In **The `surface` section** paragraph, "read them from the **Gate** file"
gains ": a `FAIL surface` line there is a CRITICAL (**Severity**, item 5), never a WARNING".

**R6 — Deviations.** The bullet "A departure from the design with no entry at all is a
CRITICAL: the failure is the silence, not the departure." gains:

```
  That holds when the design contradicts itself and the code follows one of the two items:
  the silence is still CRITICAL, and you also append a `spec-change:design` entry whose
  **Clause** is the first item, **Said** its words, and **Found** the second item quoted with
```
