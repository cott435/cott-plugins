the order listed under **Phases**, one chat and one commit each, by plugin-dev's

## Breaking changes to list in `CHANGELOG.md`

1. Implementers run in parallel by default, and a batch holds every ready row's step (PLAN
   alone). `/dev-team:run-package <pkg> --serial` is the 2.1 loop.
2. The stop gate no longer runs `repo`-scope pytest rows of `docs/constraints.md`; the record
   says `SKIPPED <row>: repo-scope pytest is CI's`, and CI still runs them.
3. New entries, reports, change files and decision stubs go to `docs/packages/<pkg>/…`
   (`decisions/`, `deviations/`, `reviews/<section>/`, `changes/`). `docs/deviations/`,
   `docs/deviations.md`, `docs/reviews/` and `docs/changes/` are still read; an entry is edited
   where it is. No migration.
4. The tester's spawn field `Adopted code:` is `Design mode: new | document | delta`, and the
   tester may return `Result: spec-change`.
5. A designer or implementer never writes `docs/decisions.md`: stubs and `Applied:` lines go
   to the section's inbox and a hook merges them. A session without the hook fails the run
   gate on an unsynced inbox; `python3 <plugin>/hooks/sync_decisions.py --all` repairs it.
6. A gate retry amends only when `HEAD` is the run's own commit; otherwise it is a second
   commit with the same trailer, so a run may have two commits.
7. The `.dev-team/stop` marker is per section, `.dev-team/stop/<pkg>/<section>`; the deviation
   heading gains `— <k>` and the docstring tag `(deviation <date>-<k>)`. Old spellings still
   match.

## Standing facts for every phase

- Mechanical rows need `ruff` on PATH and `pytest` importable by `python3`
  (`python3 -m pip install pytest`). On the planning container (ruff 0.15.8) the 2.1 baseline
  is hook-events 66/67 — `gate-elsewhere-mixed` fails on ruff's changed output format, not on
  this plugin — and state-cases 58/58, contracts 36/36. A phase's pass bar counts a case that
  fails identically at the phase's start as not this phase's.
- Every behavioral row's baseline `previous` is the 2.1.0 file (the merge-base with `main`).
  Existing evals whose prompts or expectations spell a path or field 2.2 moves were updated in
  phase 0 to the 2.2 spelling, each with a `note_2_2` field naming the change; the baseline
  configuration is expected to fail those lines, and its pass rate is recorded, not required.
- Regression rows (an existing set rerun on a changed target) pass when every expectation
  passes for `with_skill`; the baseline's rate is logged for the comparison.
- Platform-fact results for Claude Code facts are written back to plugin-dev's
  `skills/plugin-anatomy/references/hooks.md` as `[proven: <log>]` — a different plugin's
  file, so `run-phase` records it as *noticed: write back to plugin-anatomy* in the ledger and
  a small change to plugin-dev follows. F3 is an import-linter fact, not a Claude Code one:
  it is written back to this plugin's `skills/workspace-scaffold/SKILL.md` §3, the owner of the
  `(name)` rule, by the phase-0 chat itself (one `[proven: <log>]` or one corrected sentence).
