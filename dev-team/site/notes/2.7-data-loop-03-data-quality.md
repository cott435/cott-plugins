# 03 — the `data-quality` skill

Phase 3. Adds the knowledge skill that tells a designer and an implementer how a section is
designed and built from a data profile: one handler and one test per kind, a treatment only
where the user decided it, every rejected or altered row kept with its kind as the reason, and
unclassified rows quarantined. The designer reaches it through its `Skills to invoke:` field
(the row's `builds with`), the implementer through the design's **Skills used**; neither agent
file changes. It closes the gap between a profile that lists kinds and a section that handles
each of them: without it the designer treats the kinds as ordinary **Quirks** and nothing fixes
the reject record or the default for a row that matches no kind.

## Decisions

- **No trigger eval.** Agents invoke the skill by name, from a contract cell; no other dev-team
  knowledge skill has a trigger set, and a description tuned to fire in a user's session would
  be a second, unwanted entry point. The description still says when it applies, for the
  architect, who lists plugin skills with `ls ${CLAUDE_PLUGIN_ROOT}/skills`.
- **`user-invocable: false`, and no `disable-model-invocation`**: agents must be able to invoke
  it with the Skill tool, and a user has no reason to type it.
- **The kinds table sits under the design's item 4, Workflow / pipeline**, as a table after the
  steps. The design template has no item to add (`agents/designer.md` is unchanged), and the
  handlers are workflow steps.
- **The reject record's shape is the package's**, not this skill's. The skill fixes what it
  holds (the row's key, the kind id as the reason, the treatment applied, and for a `repair`
  the value before) and leaves the store to the contract.

- **Every row a kind touches has a reject-record entry**, `flag` and `repair` included. A
  repaired row is in the output and in the record; a flagged row is in the output, marked, and
  in the record with the treatment `flag`. How a flag is marked on the row is the design's.
- **A kind waiting on its decision shows `D<n> (open)` under `decided by`.**
- **The built section carries every check in the profile's Checks table**, not only the checks
  of the verified kinds: that is how a row of an `unverified` kind, or of no kind, is seen to
  fail and lands in `unclassified`.
- **A kind whose check compares rows is tested with the rows it is compared against**, taken
  from `accepted` (a duplicate's first print, the neighbouring rows of a key).

## Specification

### `skills/data-quality/SKILL.md`

Reference: `plugin-anatomy` `references/skills.md`. Frontmatter, verbatim:

```yaml
---
name: data-quality
description: How a data-heavy section is designed and built from its data profile - one handler and one test per kind of failing row, a treatment only where the user decided it, every rejected or altered row kept with its kind as the reason, and unclassified rows quarantined. Invoke when a section's contract row lists dev-team:data-quality under builds with, before designing or building that section. Not for a section that only passes data through.
user-invocable: false
---
```

Body, in this order, headings spelled exactly:

1. `# Building a section from its data profile` and a three-line opening: the profile is the
   `docs/sources/<token>.md` among your **Source probes** whose title line says `stage`; it was
   written from all the real data; this skill is how its kinds become code.
2. `## Reading a profile` — which headings to read and for what: **Observed schema** (the shape
   to parse), **Checks** (each rule and what it judges against), **Quirks** (the kinds: id,
   checks, count, proposed treatment, its `D<n>`, `verified` or `unverified`),
   **Unexplained** (how much is still unsorted), and `<token>.sample.json` (up to five rows per
   kind, and `accepted`). A kind marked `unverified` is not designed for: its rows are
   unclassified.
3. `## The design's kinds table` — under the design's **Workflow / pipeline**, after the steps,
   one row per verified kind:

   `| kind | rule | handler | treatment | decided by |`

   `kind` is `K<n>` and its name; `rule` is the check in the design's own words; `handler` the
   function that isolates and treats it; `treatment` one of `repair`, `drop`, `quarantine`,
   `flag`; `decided by` the `D<n>`, `D<n> (open)` for a kind quarantined while its decision
   waits, or `—` for a kind that needs none.
4. `## Treatments` — a treatment is `repair` or `drop` only where its `D<n>` in
   `docs/decisions.md` reads `Status: decided`, and it is what the decision says, which may
   differ from the profile's proposal. A kind whose `D<n>` is open is quarantined, and listed
   under the design's **Open questions** as waiting on that decision. `quarantine`: the row is
   kept out of the output and kept in the reject record. `flag`: the row passes, marked.
5. `## The reject record` — every rejected or altered row is kept: its key columns, the kind id
   as the reason, the treatment applied, and for a `repair` the value before. Nothing is
   rewritten or removed silently. A repaired row is in the output and in the record; a
   flagged row is in the output, marked, and in the record with the treatment `flag`. Where it is stored is the package contract's to say.
6. `## Unclassified rows` — a row that fails a check and matches no kind in the table is
   quarantined with the reason `unclassified`. So a built section sorts every input row into
   exactly one of: accepted, a decided kind, `unclassified`. The section runs every check in the
   profile's **Checks** table, so a row of an `unverified` kind is caught and lands here.
7. `## Tests` — the design's **Tests** names one case per kind, run on that kind's rows in
   `<token>.sample.json`, asserting the treatment and the reject record's reason; one case that
   the `accepted` rows stay accepted and unchanged; and one that a failing row of no kind is
   quarantined as `unclassified`. A kind whose check compares rows (a duplicate, an
   out-of-order timestamp) is tested together with the rows it is compared against, from
   `accepted`.
8. `## What the README says` — the section README's **Pipeline / workflow** lists the handlers
   in order with their kind ids, and **Implementation notes** names the profile and the round
   it was built from. The design's **Skills used** lists `data-quality`, so the implementer
   invokes it too.
