# 02 — the gate record

Phase 02. The stop gate has always written a record per section and the reviewer has always
read it; `status.py` never did. So a section whose implementer blocked after its hand-back,
or was let through on its third red attempt, moved to REVIEW on its README alone and shipped
(open items 1 and 14). This phase makes the record say which commit it speaks for, makes a
marker stop write a record instead of deleting the only trace, and makes `status.py` hold
the row: BLOCKED for a blocked or let-through section, IMPLEMENT for a run that died between
attempts. After it, `status.py <pkg>` shows the held row and a `next:` line with the two
commands a user can type. The driver's own question about such a row arrives in phase 9, the
implementer's wording in phase 6 and the reviewer's in phase 8; nothing here changes what an
agent is told.

## Decisions

- **The record's `commit:` is computed by `status.py`,** in a new `gate_commit`, and the gate
  imports it. The gate has no parser of its own (its docstring's last line), and the reader
  and the writer must compute the same commit.
- **Commits are compared by prefix.** The record holds a short sha; `status.py` accepts a
  record whose `commit:` is a prefix of the section's current full sha, seven characters or
  more. No assumption about `core.abbrev`.
- **Uncommitted changes under the section's code, unit tree or README make the record
  stale.** The record describes a commit, and the tree is no longer that commit.
- **A marker stop rewrites the record around the earlier check lines.** The design says the
  gate "appends to the record this run already wrote" and also that line 1 is the header and
  the last line is `result:`. Both hold when the new record is: a new header, the `commit:`
  line, the earlier record's check lines, the marker's line, the `result:` line. The earlier
  header and `result:` line are dropped. "This run already wrote" is decided by the attempt
  counter: it exists only after a gate attempt of this agent.
- **A round-1 half pair counts as covering the code.** After *review anyway* the reviewers
  run; with one report in, the row must read REVIEW (`review r1 lacks its b report`), not fall
  back to BLOCKED.
- **Evidence never holds ` · `.** The row is ` · `-separated, so a blocker's text has each
  ` · ` replaced by `, ` before it is printed.
- **`--report` records gain the `commit:` line too,** so line 2 means one thing in every
  record. `status.py` ignores them by their slot.
- **The let-through and retry messages on stderr keep their 2.3 text here.** Phase 6 changes
  them together with the implementer's own words.

## Specification

### `status.py`

`gate_commit(pkg, section) -> str | None`: the full sha of the newest commit touching the
section's code (nested sections excluded, as `_paths` gives it), `tests/unit/<section>` and
its README (`interface.md` for `surface`); `None` when no commit does. The intent tree is not
among the paths, so a tester's regeneration never makes a record stale.

`gate_record(pkg, section) -> dict | None`: reads
`<root>/.dev-team/gate/<pkg>/<section>.txt` and returns `None` (the record is absent or
stale) when any of these holds:

- the file does not exist or has fewer than three lines;
- line 1 does not match `^dev-team gate — (attempt (\d+)|blocked|spec-change|report) — `;
- no line starts `commit:` (a pre-2.4 record);
- `uncommitted(...)` is true for the paths `gate_commit` reads;
- the `commit:` value is `none` while `gate_commit` is not `None`, or is under seven
  characters, or is not a prefix of `gate_commit`'s sha.

Otherwise it returns `slot` (`attempt`, `blocked`, `spec-change` or `report`), `attempt` (the
number, or `None`), `result` (the text after `result: ` on the last non-empty line), `fails`
(every line starting `FAIL`), and `blocked` (the text after `blocked: ` on the line that
starts so, or `""`).

`_review_covers(pkg, section) -> bool`: true when a review round exists, its `Commit:` is
readable, and `changed_since(rsha, code, unit, intent, readme, skip_regen=...)` is `None`,
the same expression rule 7 uses. Rule 7 calls it too.

In `section_state`, **rule 1** gains, after the decision and review-cap checks: when the
README exists, `_review_covers` is false and `gate_record` is not `None`:

- `slot == "blocked"` and `result == "blocked"` → `("BLOCKED", "gate blocked: <blocked>")`,
  with `(no reason given)` for an empty text and each ` · ` replaced by `, `;
- `slot == "attempt"` and `result` starts `letting the run stop` →
  `("BLOCKED", "gate let through after 3 attempts, <k> failures")`, `<k>` the number in the
  result line (`with <k> failure`).

**Rule 6** gains, after its two existing checks: under the same three conditions, `slot ==
"attempt"` and `result` starts `not done (attempt ` → `("IMPLEMENT", "gate <result>")`, which
prints `gate not done (attempt <n> of 3)`.

Any other record changes nothing: `pass`, a `report` slot, a `spec-change` slot.

`next_command`: after the decision branch and before the review-cap branch, a BLOCKED row
whose evidence starts `gate ` returns

```
/dev-team:run-package <pkg> <section> --step IMPLEMENT (run it again) or /dev-team:run-package <pkg> <section> --step REVIEW (review anyway)
```

The docstring's rules 1 and 6 become:

```
1. **BLOCKED** — an open decision with no assumption binds the section (`docs/decisions.md`
   entry with `Status: open`, no `Assumption if unanswered:`, `Scope:` covering `repo`, the
   package or the section); or the newest review round says `request changes` and the cap is
   hit: round 3 or later, or round 2 whose `Convergence:` line has one or more prior unfixed;
   or the section has a README, no review round covers its code, and the stop gate's record
   for its current commit ends `result: blocked` or `result: letting the run stop after 3
   attempts …`.
```

```
6. **IMPLEMENT** — no README (`<section path>/README.md`; for `surface`,
   `docs/packages/<pkg>/interface.md`); or the intent tree, regeneration and `intent tests current with design`
   commits skipped, is newer than the README; or the section has a README, no review round
   covers its code, and the gate's record for its current commit ends `result: not done
   (attempt <n> of 3)`, a run that died between attempts.
```

A new paragraph goes after the paragraph that starts `Ready:` and before `**Scaffold.**`
(phase 3 puts its `**Evidence.**` list directly above this one):

```
**Gate record.** `.dev-team/gate/<pkg>/<section>.txt`, written by `hooks/gate_on_stop.py` on
every implementer stop. It speaks for the commit its `commit:` line names: the newest commit
touching the section's code, `tests/unit/<section>` and its README, the intent tree left out.
A record whose `commit:` is not that commit, a record with no `commit:` line (written before
2.4), a missing record, and a record read while those paths have uncommitted changes are all
treated as absent, and the row is derived without it. A record whose header slot is `report`
(`/dev-team:pair`'s wrap-up) or `spec-change` never holds a row. Once a review round's
`Commit:` covers the code the review speaks and the record is not read, which is what makes
the user's *review anyway* stick.
```

Keep both paragraphs free of `**Capitalised bold**` words other than `**Gate record.**`
itself: nothing in them is a field the implementer's **Inputs** defines.

### `hooks/gate_on_stop.py`

- `write_records(cwd, targets, header, lines, outcome)` builds each section's text as
  `header`, then `commit: <sha>` where `<sha>` is `status.gate_commit(pkg, section)[:7]` or
  `none`, then `lines`, then `outcome`. Every caller passes the parts; `--report` too.
- The marker branch of `gate`: for a marker whose first line is `blocked` or `spec-change`,
  before `marker.unlink()`:
  1. `reason` is the marker's first line, lowercased; `detail` its second line, stripped, or
     `(no reason given)`.
  2. `carried` is every line of the section's existing record whose first word is one of
     `PASS`, `FAIL`, `ELSEWHERE`, `TOLERATED`, `TIMEOUT`, `SKIPPED`, `MEASURED`, kept only
     when the attempt counter file exists; otherwise empty.
  3. The record is written: header `dev-team gate — <reason> — <stamp> — section
     <pkg>/<section>`, the `commit:` line, `carried`, the line `<reason>: <detail>`, and the
     last line `result: <reason>`.
  The marker is then deleted, the counter cleared, exit 0, with no check run, as before. In
  the fallback (no section in the transcript) the same record is written for each section
  whose marker was found, with ` (from diff)` after the section name.
- `.dev-team/stop/scaffold` writes no record, as before.
- The docstring's steps 3 and 6 say the above, and after the `--report` paragraph, before
  the line "The parsers are status.py's, imported", these lists go in at column 0:

```
The record's lines, in order (status.py and the reviewer read them by these names):

1. **header** — `dev-team gate — <slot> — <stamp> — section <pkg>/<section>`.
2. **commit** — `commit: <short sha>`, the newest commit touching the section's code, unit
   tree and README (status.py's `gate_commit`), or `commit: none`.
3. **checks** — one line per check; its first word is PASS, FAIL, ELSEWHERE, TOLERATED,
   TIMEOUT, SKIPPED or MEASURED.
4. **marker** — `blocked: <the marker's second line>` or `spec-change: <the entry heading>`,
   on a marker stop only.
5. **result** — the last line, `result: <value>`.

The header's slot:

1. **attempt** — `attempt <n>`, a stop that ran the checks.
2. **blocked** — the implementer's marker said `blocked`.
3. **spec-change** — the marker said `spec-change`.
4. **report** — `--report`, run by hand.

The `result:` values:

1. **pass** — no FAIL line; a note follows for ELSEWHERE, TIMEOUT and SKIPPED lines.
2. **not done** — `not done (attempt <n> of 3)`: a FAIL before the third attempt.
3. **letting the run stop** — `letting the run stop after 3 attempts with <k> failures`.
4. **blocked** — a `blocked` marker stop.
5. **spec-change** — a `spec-change` marker stop.
6. **fail** — `fail (<k> failures, report since <rev>)`, `--report` only.
```

No text in `hooks/*.py` may name a typed dev-team command: the claim `every hook matcher and
agent_type names an agent this plugin ships` reads `dev-team:` followed by any other word as
an unknown agent.

### State cases

## Deviations

- **`gate-blocked-dirty`'s expected evidence.** The note said `ingest · REVIEW`, evidence
  `/^uncommitted: /`. The case expects `/^no review$/`. With no review round, rule 7 returns
  `no review` before it compares code with a review commit, and no other rule prints
  `uncommitted:` for a dirty code file, so the note's evidence could not be produced without
  changing rule 7. The case still pins the rule: the same record without the dirty file is
  `BLOCKED` (`gate-blocked`), with it `REVIEW`.
- **`gate-marker` also changed.** The note listed `gate-own-marker` as the existing marker case
  to update and said every other record case passes unchanged. `gate-marker` (counter 1, marker
  `blocked` / `D4 needs an answer`) asserted that `.dev-team/gate` stays absent, which the
  spec's marker record contradicts. Its setup is unchanged; `.dev-team/gate` left its `absent`
  list and it now checks `blocked: D4 needs an answer` and `result: blocked`. `gate-own-marker`'s
  marker has no second line, so its `blocked:` line is `blocked: (no reason given)`.
- **Rule 7 and `_review_covers`.** The note said rule 7 calls `_review_covers`. Rule 7 needs the
  first commit after the review for its evidence, which a bool cannot give, so the expression
  is one helper, `_code_after_review`, that both `_review_covers` and rule 7 call.
- **The hook-events README has no case table.** Its cases are described in paragraphs, so the
  new rows went in as one paragraph, **The 2.4 record**, naming each case.
- **Small consequences of per-section `commit:` lines.** `write_records` now writes each
  section's own text, so `--report` prints every record it wrote (one, in every current case)
  rather than one shared text; and the fallback records and deletes every marked section it
  found, where 2.3 deleted only the first.
