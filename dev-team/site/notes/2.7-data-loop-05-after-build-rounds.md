# 05 — after-build rounds

Phase 5. A marked section its reviewers approved is not DONE until a profile round over its own
output finds nothing unexplained. `status.py` gains the second PROBE condition (approved, and
the code is newer than the newest round line's commit); the profiler gains rounds 1 and later:
it points the built section at a store under `.dev-team/data/<token>/work/`, runs it over the
stored input, re-runs every check on what the section accepted and rejected, and either writes
`clean` or hands new kinds to a verify run, which writes one `spec-change:design` entry so the
existing rule 4 re-opens the section. It closes the gap that only built code shows what the
rules missed, and that today's quarantine table is read by nobody.

The cap on rounds, and `Mode: defer`, are phase 6. After this phase a section whose rounds keep
finding kinds loops until one is clean; phase 6 bounds it.

## Decisions

- **The second condition fires only where the state would otherwise be DONE.** `section_state`
  derives the state with the condition off; when that is DONE and a round is due, the state is
  PROBE. So an open change file, a FIX row or a paths re-open is never preempted by a profile
  of code about to change.
- **"Newer than" is the section's code as rule 7 reads it**: its path, `tests/unit/<section>`,
  `tests/intent/<section>` and its README. A round is due when the newest round line's commit
  is `none` (only round 0 has run) or `changed_since(<that commit>, <those paths>)` is not
  `None`.
- **The round number is the newest line's round plus one**, and `Commit:` is
  `section_commit(pkg, section)`, the commit `--rounds` prints.
- **A clean round needs no verify run** (design). The profile run writes `clean` when the round
  adds no kind, **Unexplained** is zero, no kind is `unverified`, and no accepted row fails a
  check. Otherwise it writes `pending verify`.
- **The verify run at round 1 or later ends `new kinds: K<a>, …`** and writes the ledger entry,
  whether the kinds verified or stayed `unverified`: either way the design must account for
  the rows. Decision stubs for new `repair` or `drop` kinds are raised as at round 0.
- **`--profile` with nothing due now prints the next round** once the section has a README:
  `Round:` newest plus one, `Commit:` the section's commit (design, **Decisions taken**,
  planning). Without a README it stays round 0, as phase 2 left it.
- **A section that cannot be pointed at another store returns `blocked`**; the profiler never
  runs it against the project's real store.
- **A section that writes no store needs no pointing.** A pure entry point (rows in, accepted
  and rejected rows out) is called over the stored input and what it returns is written to
  `<Store>work/` by the program. `blocked` is only for a section that writes a store and
  documents no setting for where.

- **A `flag` kind does not stop `clean`.** A flagged row stays in the accepted output and still
  fails its check, by design. "An accepted row fails a check" therefore means: fails a check
  and is not a row of a verified `flag` kind carrying that kind's mark. Written into the
  design's **Decisions taken**, Origin *planning*.
- **A later round may add checks.** A new kind needs a check that isolates it; the round
  appends rows to the **Checks** table and checks to the program, and changes no existing one.
- **The verify run marks a round's new kinds too**: it rewrites the last two fields of each
  kind the round added (`D<n>` or `no decision needed`; `verified` or `unverified`) before it
  appends the round's closing line.
- **Behavioral baselines here are the previous phase's commit, not `previous`.** `previous` is
  the merge-base with `main`, which has no `agents/profiler.md`. Rows 5.5 and 5.6 run with
  `--baseline <phase 1's commit>`, the SHA in the ledger's phase 1 row.

## Specification

### `status.py`

- Rule 3 of the docstring gains, after phase 2's sentence: "or, for a section that would
  otherwise be DONE, a `stage:` source whose newest round line's commit is `none` or older than
  the section's code (rule 7's paths): the built section has not been profiled."
- **Evidence** item 7 gains: `stage:<token> r<n> not profiled on built code` (the newest line's
  commit is `none`) and `stage:<token> r<n> <sha> older than code <sha>`.
- The `--profile` list: **Round** — "the newest round line's round for `verify` and for a
  revision; that round plus one when a round over the built section is due, or when nothing is
  due and the section has a README; `0` with no round line". **Commit** — "the section's code
  commit, as `--rounds` prints it, at round 1 and later; else `none`".
- `section_state`: the body below rule 3 moves into a helper that returns the state without the
  after-build condition; when it returns DONE, each `stage:` source is tested for a due round
  and the first one due returns `PROBE` with the evidence above. The verdicts `pending verify`
  and `revise: …` on a round ≥ 1 line are handled by phase 2's rule unchanged: they are tested
  first, before rule 4, at any round.
- A newest line `new kinds: …` makes nothing due by itself: the open `spec-change:design`
  entry puts the row at DESIGN (rule 4). Once the section is rebuilt and approved again, its
  code is newer than that line's commit and the next round is due.

### `agents/profiler.md`

- Description: after the `Mode verify` sentence, add: "After the section is built and approved
  it profiles the section's own output on the same checks, and new kinds reopen the design."
- **Inputs** item 4, **Round** — "`0` before the section is designed; `1` or more on the built
  section". Item 6, **Commit** — "the section's code commit at round 1 and later; `none` at
  round 0".
- **Hard rules**, the write list gains: "on a verify run at round 1 or later, the section's
  ledger `docs/packages/<pkg>/deviations/<section>.md`". And: "Never run the section against
  the project's real store. Never claim `clean` while **Unexplained** is above zero, a kind is
  `unverified`, or an accepted row fails a check (a row of a verified `flag` kind, carrying
  its mark, aside)."
- `### Mode: profile` gains a second numbered list, **Round 1 and later**:
  1. Read the profile, `docs/decisions.md` for each kind's decided treatment, and the section's
     shipped README: **Entry points and interfaces**, and **Configuration** for the setting
     that names its store.
  2. Point the section at `<Store>work/` through that setting (an environment variable on the
     command, never an edit to a file under the package) and run its entry point over the
     same input round 0 read: the location `Data:` names, or `<Store>input/` when it was pulled. No such setting → `Result: blocked`,
     `Blocked: <section> cannot be pointed at another store: <what the README says>`.
  3. Re-run the program with the round number: every check on the rows the section accepted
     and on the rows it rejected, written to `<Store>rounds/<n>/`, each count printed beside
     round `n-1`'s from `<Store>rounds/<n-1>/counts.json`.
  4. Examine only what is new: accepted rows that fail a check, and rejected rows that match no
     decided kind. Group them as at round 0, at most 25 kinds.
  5. Append to the profile and change no existing line: any new kind under **Quirks**
     (`unverified`), a `### Round <n>` block under **Rounds**, new example rows in
     `<token>.sample.json`.
  6. Append the round line, with `Commit:` as the commit: `clean` when the round added no kind,
     **Unexplained** is zero, no kind is `unverified` and no accepted row fails a check; else
     `pending verify`.
- `### Mode: verify` gains step 6: "At round 1 or later, in place of the `kinds:` line: append
  one entry to the section's ledger per `planning-templates` `references/deviations-entry.md`,
  heading `## <pkg>/<section> — <date> — spec-change:design — <k>`; **Clause** `design §4
  kinds table`; **Said** the design's kinds, by id; **Found** each new kind with its count and
  denominator and `docs/sources/<token>.md` **Quirks**; **Why** `the built section's output
  holds rows no kind accounts for`; **Status** `open`; **Raised by** `profiler — <Run:>`;
  **Resolved by** `—`. Then the round line `new kinds: K<a>, …`."
