# 05 — templates-and-commit-rule

Phase 5. Moves the documents' shapes to where 2.2 writes them, before any agent writes there:
the ledger entry's path and its `— <k>` heading with the `resolved` owners (W2, F13), the change
file under its package with one file per affected package, the review report under its section
with `Commit:` from `status.py --rounds` (F12), the constraints template's one sentence on
`repo` pytest rows, the templates index, and `git-workflow-and-versioning` §Project convention:
the 2.2 retry commit rule and the inbox joining what an agent stages. No agent changes here;
each cites these files, and phases 6 to 8 bring the citations into line. The gap it closes:
the owners of every heading other files parse must move first, or `check-contracts` cannot
hold the readers to them.

## Decisions

- **`<k>` is the entry's 1-based sequence in its own file**, counted over `## ` headings,
  computed by the writer at append time. Reason: the design (F13); a number needs no naming.
- **`Resolved by:` on a `resolved` spec-change is `<role> — <Run:>`** (`designer — run-package
  data`), the same form as `Raised by:` and as the architect's `plan-package data`. Reason:
  the design writes `<sha>`, but the commit that carries the status line does not exist when the
  line is written and §Project convention allows no second commit; the architect's existing
  rule and `sync-plan`'s "this run's own commit does not exist yet" set the precedent.
- **Rule 4's amend test is the summary prefix `<pkg>/<section>:`**, read with
  `git log -1 --format=%s`. Reason: the design's Gate retry commit decision.
- **Rule 2 names `docs/decisions.md` beside the inbox** as a file the run stages when its
  inbox changed. Reason: the design's *Central ledger commit* decision (planning).

## Specification

### `deviations-entry.md`

Title: `# The section ledger, `docs/packages/<pkg>/deviations/<section>.md` — one entry per deviation or spec-change`.

First paragraph, replacing the current one:

> One file per section, so agents that run in parallel on different sections never write the
> same file. A new file starts with the line `# Deviations — <pkg>/<section>`. Two older
> locations are still read, and an entry is edited in the file that holds it: the 2.0 section
> file `docs/deviations/<pkg>/<section>.md`, and the pre-2.0 `docs/deviations.md`. Every new
> entry goes to the path above.

Heading line: `Entry heading: `## <pkg>/<section> — <date> — <kind> — <k>`, `kind` one of …,
`<k>` the entry's 1-based sequence in this file (count the `## ` headings and add one). A
reader accepts a heading without `— <k>` (a 2.x ledger) and treats `k` as absent; a writer
always adds it, so two same-day entries of one kind are told apart, and a test's docstring tag
names the entry as `(deviation <date>-<k>)`.`

Item 6 **Status**: `… `open | resolved` for a spec-change. Who sets `resolved`: the designer on
the `spec-change:design` entries its rewrite answers, the tester on the `spec-change:test`
entries it regenerates, the architect on a `spec-change:contract` it edits for, each in the
commit that answers it; `sync-plan` sets it on any spec-change `status.py` already counts as
answered at the package close.`

Item 8 **Resolved by**: `… `<role> — <Run:>` (`designer — run-package data`) or the report or
change-file path that closed it; `—` while open. Never the closing commit's own sha, which does
not exist when the line is written.`

The "Written by" sentence adds `pair` and lists the tester's `spec-change:design` (W1).

### `git-workflow-and-versioning` §Project convention

Rule 2 **Staging**, after the first sentence: `The section's decisions inbox
`docs/packages/<pkg>/decisions/<section>.md` joins them when the run wrote to it, and so does
`docs/decisions.md`, which the sync hook merged it into: a `D<n>` a committed design cites
must exist in a commit.`

Rule 4 **One commit per run**, replacing the exception sentence: `The one exception to "never
two": an implementer whose stop gate exits 2 stages its fix and then looks at `git log -1
--format=%s`. When the summary starts with its own scope (`<pkg>/<section>:`), `HEAD` is its
commit and it runs `git commit --amend --no-edit -- <paths>`, the paths being every path the run
has written. Otherwise `HEAD` is a parallel run's commit, and amending it would rewrite another
agent's work: it makes a second commit with the same summary and the same trailer instead. A
run that stops on a blocker commits nothing unless its agent says otherwise.`

Message table, reviewer row: `| reviewer | `review <pkg>/<section>` | `r<n>-<letter>: <verdict> (<k> critical)` — `review data/ingest: r1-a: request changes (2 critical)`; the report is under `docs/packages/<pkg>/reviews/<section>/` |` (the colon after the section, as `reviewer.md` **Commit** already writes it; the table's old example lacked it).
