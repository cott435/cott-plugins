# 06 — Architect at the close: Call paths for a package planned before 2.6

Phase 6. At the package close the architect writes **Call paths** for a contract that has
none, as built, from `status.py --paths <pkg>`, and for each command deeper than the hard
budget writes a change file proposing where the path is cut; `sync-plan`'s "nothing to collect"
exit holds only once the heading exists. It closes the design's fourth workflow: a package built
under 2.5 or earlier gets a true record of its paths at its next close, and a reviewed proposal
for every path that is too deep, with nothing rebuilt until the user approves.

## Decisions

- **Written as built, every frame.** The as-built form (template item 5) copies the tree:
  private frames, `[indirect]` frames, each named `<owner>.<name>`. The close writes what the
  code does; a target the code does not meet goes in the change file.
- **Budget 8, no `D<n>`** (design amendment, **Decisions taken**): an entry past the budget ends
  `— past budget, see docs/packages/<pkg>/changes/paths-<command>.md`.
- **The change file's slug is `paths-<command>`**, suffixed `-2`, `-3` if taken, per **Edits**.
  Its **Affected sections** are the sections whose frames the proposed cut removes or moves;
  **Contract changes** holds the entry as it should read after the cut; **Downstream impact**
  comes from the consumer grep, as for any change file.
- **Step 8, after the sweep.** The heading is written after steps 1–7, so the W2 sweep and the
  applied items are done before the contract's new item is archived and written; one archive
  copy per run still (**Edits**: once per file per run).
- **A package with no command writes `- none (no commands)`.** The heading exists either way,
  so phase 3's readiness test is answered.

## Specification

### `architect.md`, **sync-plan — the package close**

New step after step 7:

> 8. **Call paths.** When the contract has no **Call paths** heading, run `python3
>    ${CLAUDE_PLUGIN_ROOT}/skills/status/scripts/status.py --paths <pkg>` once and write the
>    heading in the template's **As built** form (`references/package-contract.md`, item 5):
>    one entry per `command:` block, `(budget 8)`, one path per effect leaf of the block —
>    every frame of the tree from the command to that leaf, numbered, each `<owner>.<name>`
>    with `<name>` the frame's printed name and `<owner>` the section whose path holds its file
>    (`cli` for `cli.py`, `pipelines` under `pipelines/`), `[indirect]` frames included — the
>    leaf's callee as the effect. On `paths: no commands`, the heading's one line is `- none
>    (no commands)`. Archive the contract first (**Edits**) unless this run already did. For
>    each command whose `depth to first effect` is past 8, invoke `planning-templates`, read
>    `change.md`, and write `docs/packages/<pkg>/changes/paths-<command>.md` with `Status:
>    open`: **Change goal** the path cut to depth 8 or less; **Affected sections** every section
>    whose frame the cut removes or moves; **Contract changes** the command's **Call paths**
>    entry as it should read after the cut, and any **Section interfaces** or **Pipelines**
>    change the cut needs; **Downstream impact** from the consumer grep of step 6. That
>    command's line in the contract ends `— past budget, see <the change file's path>`, and
>    carries no `D<n>`. **Section interfaces** gains nothing for an as-built frame: the owner
>    rule binds entries written at PLAN, and the frames here are the code's. A contract that
>    already has the heading gets nothing here: its paths are the paths review's to judge.

  the harness says what the command would print". The fixture has code (`cli.py` and three
  sections) and neither the prompt nor `sync-harness.md` named a `--paths` output. On a git
  copy of the tree `status.py --paths data` prints `paths: no commands` (no `pyproject.toml`),
  so eval 3's prompt now gives that line, and its expectations 8 and 9 require what step 8
  makes of it: `## Call paths` with `- none (no commands)`, and the return's
  `| Call paths | written as built (0 commands, 0 past budget) |`. A 2.5.0 close fails both.
- **The eval 3 harness answer.** `sync-harness.md` answered `Resolved by:` "when no commit sha
  exists" with `run-package data (sync-plan), <today>`, against expectation 1's `7b2f0a1`;
  both configurations took the harness answer in iteration 3. The answer now points at the
  newest approving review's `Commit:` line, and expectation 1 accepts `approve @7b2f0a1` too,
